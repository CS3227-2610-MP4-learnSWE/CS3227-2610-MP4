# STU-03 cap experiments summary: 30 October 2026

## Direction and completed work
The user asked for evidence-based limits for the STU-03 study companion before the spec was finalised. In a side session, a worktree and branch `exp/stu03-caps` were created from `master` (`e544ea5`). Scripts and prompts were built offline first (fake LLM), then run live in seven phases, each only after the user said go and sent a SoCLaaS dashboard screenshot: 1 (`/models` and a tiny chat), 2 (reply length per mode), 3 (input length and history), 4 (extraction and injection attempts), 5 (10-call burst, no 429), 6 (270-call factorial sweep of output cap, answer-length instruction and history across the three modes, scored by a deterministic usefulness rule) and 7 (the phase 4 attacks again with the short-answer instruction). The user keyed the API key into a git-ignored `.env`; it was never read, printed or stored.

Results (full tables in `workflow/experiments/stu03-caps/RESULTS.md`): a short-answer instruction is the main saving (explain $0.000408 to $0.000176 per call; caps hint 100, explain 200, help 150 suffice); input 1,000 characters, history 4 messages (kept for usefulness to students, the user's decision; 4 messages cost 14% to 29% more than none and did not change usefulness in our single-turn tests), timeout 15 s, our own rate limits 10 per minute and 100 per day per student. Prompts did not prevent answer leaks under attack (about a third to a half of hint attempts leaked or narrowed the answer, with both instruction variants; a pasted question was answered in full), so server-side checks are required.

## Verification and limits
Every phase's call count matched the dashboard difference the user read; total 347 billed chat requests, $0.065724 (`/models` is not billed). The fitted token prices predicted phase 6's cost (0.0513) to the dashboard (0.0513). The attack replies in phases 4 and 7 were read manually; the automatic leak flag missed 3 of the 6 problem replies in phase 7. The hint usefulness rule was relaxed once after seeing the data (reported both ways). Small samples, one model alias, canned history, no over-refusal, rate-limit or concurrency test. No product code or tests were changed or run, no secret was committed, and nothing is committed or pushed yet.
