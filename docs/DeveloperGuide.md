# Developer Guide — Current Preview

## Architecture and boundaries

The React/TypeScript frontend uses Vite, React Router, Material UI/Emotion and Lucide icons. `src/frontend/src/data.ts` holds fixtures and role navigation; `state.tsx` owns temporary completion and inbox state; practice state lives in `practice/PracticeContext.tsx`. Shared layout and visual components live under `components/`; each role has a page module, with shared inbox and feedback pages. The Material UI theme is configured at the root and CSS variables coordinate custom layout/illustrations in both modes.

The student `CompanionProvider` and floating widget live at the student shell boundary, outside individual route screens. Closing hides the panel without unmounting its message/draft state. Leaving the student role or returning to login unmounts it; a browser reload also resets it. No chat is stored in local/session storage or a backend. The legacy `/student/assistant` URL opens the widget and redirects to the overview; navigation and lesson CTAs now open the widget without leaving their page.

The widget derives a current-page label from routes and sample lesson metadata only, and sends it (at most 80 characters) as untrusted text. Future authenticated sessions must scope conversation history to the signed-in account until logout/clear, restore it on reload, and retrieve bounded, authorised page content on the server. Neither page content nor chat may override fixed instructions; DOM scraping and client-provided context are not security boundaries. Session persistence and lesson content as context are not implemented (see "Study companion (STU-03)" below for what is).

BrowserRouter enables direct URLs and history. For future production hosting, configure SPA fallback and route `/api` to FastAPI. Vite proxies `/api` locally to `API_PROXY_TARGET` (default `http://127.0.0.1:8000`). The health indicator and the student Practice page fetch backend data; the health check handles checking, successful JSON, failed/malformed responses and a four-second timeout. Practice calls go only through `services/client.ts` (the single place that sets `X-Student-Id` from `config.ts`, applies a 10 s timeout built with `setTimeout` and `AbortController`, and raises one `ApiError`) and the typed functions in `services/practice.ts`, which reject responses of the wrong shape. Only the study companion calls an AI service, and only through the backend (`services/companion.ts` posts to `/api/companion/messages` with a 40 s timeout via the `timeoutMs` option of `request`; `ApiError.retryAfterSeconds` reads `retry_after_seconds` from the error body). The folder is not named `api/` because the Vite dev server would then serve `/src/api/...` modules, which the login test treats as API requests.

FastAPI exposes `/api/health` and `/api/health/ready` (process-only semantics) and the STU-02 practice attempt API: `GET /api/practice-sets/{set_id}`, `POST /api/practice-sets/{set_id}/attempts`, `GET /api/attempts/{attempt_id}`, `PUT /api/attempts/{attempt_id}/answers`, `POST /api/attempts/{attempt_id}/submit` and `GET /api/attempts/{attempt_id}/results`. The student is identified by the placeholder `X-Student-Id` header (to be replaced by SHR-01 authentication); other students' attempts return 404. Attempts live in an in-memory store behind the `AttemptStore` interface; save and submit hold a per-attempt lock from the store so a save cannot land after a concurrent submit, and the header value is trimmed before use. Modules in `src/backend/`: `practice_data` (fixture and answer key), `practice_schemas`, `practice_logic` (validation and scoring), `practice_routes` (HTTP, shared header check) and `attempt_store`; `main.py` only wires the router. The key and explanations are released only in results of a submitted attempt. OpenAPI/docs are framework-generated; explicit documentation of the 401/403/404/409/422 application errors is still a follow-up. The planned check order is not guaranteed for malformed bodies: FastAPI can return 422 before handler-level checks (see the fair comparison record and security test log). No database or real authentication dependency is present. PostgreSQL remains the agreed future database. Backend tests use HTTPX ASGI transport against the real application.

## Study companion (STU-03, first slice)

One endpoint, `POST /api/companion/messages`, sends a student message and gets `{reply, mode, withheld}`. The request has `message`, optional `history` (untrusted, at most 50 items) and a `context` (`page` is `practice` or `other`, plus `set_id`, `attempt_id`, `label`). The client never names a mode; the server picks it (`companion_service.select_mode`): `help` on other pages; `hint` on the practice page with no attempt or an unsubmitted one; `explain` only for the student's own `submitted` attempt that has no later `in_progress` attempt on the same set. A message that matches a practice question (`question_match.find_match`: normalised, whole text, two choice texts, or 80% of the question's words) forces `hint` with that question's text and code. Hint context holds question text and code only, never choices, key, explanation or key version. Check order: header 401, set/attempt 404 (another student's attempt gives the same 404 as an unknown one), context 422, message and history 422, per-student limit 429, model call, leak check. Error codes are in `workflow/specs/STU-03/plan.md`.

Modules in `src/backend/`: `companion_routes` (route, context lookup, error mapping, metadata-only logging), `companion_service` (mode selection, history trimming, message assembly), `companion_schemas`, `companion_prompts` (fixed rules per mode), `companion_help` (fixed app-help text, written from the user guide: keep them in step), `companion_config` (message 1,000 characters, history 4 messages / 2,000 characters, label 80, output caps hint 100 / explain 200 / help 150, the canned reply), `question_match`, `leak_check` and `attempt_store.list_for_student`. A hint or help reply that `leak_check.find_leak` flags (correct choice by letter or text, or a right/wrong verdict on a choice) is replaced by the canned reply with `withheld: true`. This check is deterministic and limited: paraphrased leaks pass.

`llm_client.py` is the one place the SoC LLM is called. It is generic (no practice or student wording): `SoclaasClient.complete(messages, max_tokens=, caller_id=)` posts to `{SOCLAAS_BASE_URL}/chat/completions` with `Authorization: Bearer`, 15 s timeout, one retry on timeout/5xx, per-caller sliding limits of 20 per minute and 300 per day (in memory, one process), a 12,000-character input ceiling and a 2,000-character reply ceiling. Errors are `LlmError` subclasses with fixed messages; the key is never in a message, `repr` or log. Settings come from `SOCLAAS_BASE_URL`, `SOCLAAS_API_KEY` and `SOCLAAS_MODEL` (names in `src/backend/.env.example`; put real values only in an ignored `.env`). If any is missing the endpoint answers 503 `llm_not_configured` and makes no network call. `httpx` is a runtime dependency for this. `get_llm_client` builds the client once per process on first use: an environment change needs a restart, and a client built while unconfigured stays cached until then. The shared `practice_routes.error_response` adds a `Retry-After` header whenever `retry_after_seconds` is in the error extras. `text_normalise` holds the one normaliser shared by `question_match` and `leak_check`; the leak check also strips markdown, quote marks and Unicode format characters before matching letters.

To fake the model in tests, override the dependency: `app.dependency_overrides[llm_client.get_llm_client] = lambda: fake`, where `fake.complete(messages, *, max_tokens, caller_id)` returns an `LlmReply` or raises an `LlmError`. To test the real client, give `SoclaasClient` an `httpx.MockTransport` and a fake `clock` and `sleep`. No test or CI step reads a key or calls the real service. Live checks are run by hand with approval.

## State and preview actions

The app stores no tokens, credentials or user data in browser storage. Login fields are uncontrolled and never read by application code. Sign-in/registration display a notice. Role switching is a demonstration control, not authorisation. Form drafts and selections use local React state. Uploaded files are not read or transmitted. Preview messages explicitly state that no save, generation, publication, access change or delivery occurs.

Practice uses single-answer MCQs only, including code-reading questions expressed as choices. The Practice page (`pages/Practice.tsx`) renders the set from `GET /api/practice-sets/intro-se-1` and keeps one session in `PracticeProvider`, mounted above the student routes so answers and results survive navigation (not reload). The attempt is created on first submit; the page then saves all answers in one PUT, submits and reads the results, each as a separate step so a retry repeats only the failed step. 422 `incomplete` shows the server's missing list, 409 loads the results, and a 404 `attempt_not_found` at the save, submit or results step makes one new attempt and repeats save, submit and results (once per submission; a second one shows "Try again"). Radios stay locked while a retry only has to finish a step after the save. The attempt id is held in memory only and nothing is written to browser storage. The page never computes correctness: score, correct choice and explanations are rendered, as text, from the results response, which the server releases only after a submit. Teacher demo questions (with answers) live in `teacherDemo.ts`, and `Teacher` and `Admin` are loaded with `React.lazy`, so the student bundles hold no answer key. The teacher and admin screens are still placeholder data. Still to do: real authentication (SHR-01), role/course access, persistence and filtered AI context. Tests: the mocked Playwright suite needs no backend; `tests/real-backend.spec.ts` runs only when `REAL_BACKEND=1` (project `real-backend`) against a started backend, and the CI job "Real backend end-to-end" does this: `cd src/backend; uv run uvicorn main:app --port 8000`, then `cd src/frontend; REAL_BACKEND=1 npx playwright test --project=real-backend`.

## Development and verification

Continuous integration (`.github/workflows/ci.yml`) runs on every pull request into `master` and every push to it: backend tests; frontend typecheck, lint, format check, build and Playwright tests; the token tracker's and experiment scripts' unit tests; and a dependency audit that blocks on known vulnerabilities in runtime dependencies and only reports dev-only ones. It uses read-only permissions and no secrets. Plan and decisions: `workflow/specs/CI-01/plan.md`. Deployment is not built yet; options and open decisions are in `workflow/deployment.md`.

Use the startup/check commands in [README.md](../README.md). `package-lock.json` and `uv.lock` pin resolved dependencies. No credentials are required. Ignore rules exclude local env files, generated output, virtual environments, browser traces and dependency directories. Use `npm run format` to format frontend files and `npm run format:check` to check them.

Playwright exercises real UI behaviour with intercepted health responses. Backend tests independently verify the real API. Visual checks cover desktop/mobile and light/dark modes. Native form validation is used where appropriate; accessible labels, visible focus, a skip link, reduced-motion CSS and a mobile navigation drawer are included. This is not a full accessibility certification.
