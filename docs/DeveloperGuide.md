# Developer Guide — Current Preview

## Architecture and boundaries

The React/TypeScript frontend uses Vite, React Router, Material UI/Emotion and Lucide icons. `src/frontend/src/data.ts` holds fixtures and role navigation; `state.tsx` owns temporary completion and inbox state; practice state lives in `practice/PracticeContext.tsx`. Shared layout and visual components live under `components/`; each role has a page module, with shared inbox and feedback pages. The Material UI theme is configured at the root and CSS variables coordinate custom layout/illustrations in both modes.

The student `CompanionProvider` and floating widget live at the student shell boundary, outside individual route screens. Closing hides the panel without unmounting its message/draft state. Leaving the student role or returning to login unmounts it; a browser reload also resets it. No chat is stored in local/session storage or a backend. The legacy `/student/assistant` URL opens the widget and redirects to the overview; navigation and lesson CTAs now open the widget without leaving their page.

The widget derives a current-page label from routes and sample lesson metadata only, and sends it (at most 80 characters) as untrusted text. Future authenticated sessions must scope conversation history to the signed-in account until logout/clear, restore it on reload, and retrieve bounded, authorised page content on the server. Neither page content nor chat may override fixed instructions; DOM scraping and client-provided context are not security boundaries. Session persistence and lesson content as context are not implemented (see "Study companion (STU-03)" below for what is).

The React Router data router enables direct URLs and history. For future production hosting, configure SPA fallback and route `/api` to FastAPI. Vite proxies `/api` locally to `API_PROXY_TARGET` (default `http://127.0.0.1:8000`). The health indicator and the student Practice page fetch backend data; the health check handles checking, successful JSON, failed/malformed responses and a four-second timeout. Practice calls go only through `services/client.ts` (the single place that sets `X-Student-Id` from `config.ts`, applies a 10 s timeout built with `setTimeout` and `AbortController`, and raises one `ApiError`) and the typed functions in `services/practice.ts`, which reject responses of the wrong shape. The study companion and teacher note generator call the SoC AI service only through the backend (`services/companion.ts` posts to `/api/companion/messages` with a 40 s timeout via the `timeoutMs` option of `request`; `ApiError.retryAfterSeconds` reads `retry_after_seconds` from the error body). The folder is not named `api/` because the Vite dev server would then serve `/src/api/...` modules, which the login test treats as API requests.

FastAPI exposes `/api/health` and `/api/health/ready` (process-only semantics) and the STU-02 practice attempt API: `GET /api/practice-sets/{set_id}`, `POST /api/practice-sets/{set_id}/attempts`, `GET /api/attempts/{attempt_id}`, `PUT /api/attempts/{attempt_id}/answers`, `POST /api/attempts/{attempt_id}/submit` and `GET /api/attempts/{attempt_id}/results`. The student is identified by the placeholder `X-Student-Id` header (to be replaced by SHR-01 authentication); other students' attempts return 404. Attempts live in an in-memory store behind the `AttemptStore` interface; save and submit hold a per-attempt lock from the store so a save cannot land after a concurrent submit, and the header value is trimmed before use. Modules in `src/backend/`: `practice_data` (fixture and answer key), `practice_schemas`, `practice_logic` (validation and scoring), `practice_routes` (HTTP, shared header check) and `attempt_store`; `main.py` only wires the router. The key and explanations are released only in results of a submitted attempt. OpenAPI/docs are framework-generated; explicit documentation of the 401/403/404/409/422 application errors is still a follow-up. The planned check order is not guaranteed for malformed bodies: FastAPI can return 422 before handler-level checks (see the fair comparison record and security test log). Student attempts still use memory and placeholder identity; TEA-01 uses PostgreSQL and a gated demo identity. Backend tests use HTTPX ASGI transport against the real application.

## Teacher Materials (TEA-01)

The exact schema/API are in [SharedDataContract.md](SharedDataContract.md) and [TEA-01-db-storage](../workflow/specs/TEA-01-db-storage/plan.md). Start PostgreSQL 16 with `docker compose up -d postgres` (loopback port 5433, persistent named volume). Once, create a separate empty database with `docker compose exec postgres createdb -U learnswe learnswe_db_files`. Preserve any existing database/files/.env. Set `DATABASE_URL=postgresql+psycopg://learnswe:learnswe-local-only@127.0.0.1:5433/learnswe_db_files` in your local environment. From src/backend run `uv run --env-file .env alembic upgrade head`, then `uv run --env-file .env python -m teacher_materials.seed`. The seed is idempotent; migration/seed never run at request time. No FILE_STORAGE_DIR is required.

Revision 20261102_tea01_db_storage refuses conversion if any materials exist, before schema changes; use the fresh database and upload sources again. Old uploads/drafts remain in the old database/files and do not appear in the fresh database. Populated downgrade also refuses: the old filesystem originals cannot be recreated automatically. Empty downgrade/reupgrade is supported; rollback to the old release requires its code, database/configuration and files. Do not drop/reset old data to make migration pass.
For the demo only, set backend `APP_ENV=development` and `ALLOW_DEMO_IDENTITY=true`, and copy the frontend `.env.example` to `.env` to send `X-Demo-User-Id: demo-teacher` on teacher calls. Both backend settings are required. The header is spoofable; never enable it in production. Teacher endpoints check role and membership before reading material metadata or bytes. Uploads are bounded to 10 MiB, validated as PDF/UTF-8 text, and stored in material_file.content BYTEA. The 100 MiB global original-byte budget uses transaction advisory lock 32272610 and a fresh byte sum under READ COMMITTED; oversized totals return 413 storage_quota_exceeded. Metadata/content insert and commit together; lists never load BYTEA. Downloads/generation authorise before fetching bytes. Missing content returns 503 service_unavailable. Temporary multipart spooling is closed automatically. Uploads do not create student content. The Materials page uses the shared HTTP client for multipart and blob responses while student practice keeps its existing header behavior.

## Study companion (STU-03, first slice)

One endpoint, `POST /api/companion/messages`, sends a student message and gets `{reply, mode, withheld}`. The request has `message`, optional `history` (untrusted, at most 50 items) and a `context` (`page` is `practice` or `other`, plus `set_id`, `attempt_id`, `label`). The client never names a mode; the server picks it (`companion_service.select_mode`): `help` on other pages; `hint` on the practice page with no attempt or an unsubmitted one; `explain` only for the student's own `submitted` attempt that has no later `in_progress` attempt on the same set. A message that matches a practice question (`question_match.find_match`: normalised, whole text, two choice texts, or 80% of the question's words) forces `hint` with that question's text and code. Hint context holds question text and code only, never choices, key, explanation or key version. Check order: header 401, set/attempt 404 (another student's attempt gives the same 404 as an unknown one), context 422, message and history 422, per-student limit 429, model call, leak check. Error codes are in `workflow/specs/STU-03/plan.md`.

Modules in `src/backend/`: `companion_routes` (route, context lookup, error mapping, metadata-only logging), `companion_service` (mode selection, history trimming, message assembly), `companion_schemas`, `companion_prompts` (fixed rules per mode), `companion_help` (fixed app-help text, written from the user guide: keep them in step), `companion_config` (message 1,000 characters, history 4 messages / 2,000 characters, label 80, output caps hint 100 / explain 200 / help 150, the canned reply), `question_match`, `leak_check` and `attempt_store.list_for_student`. A hint or help reply that `leak_check.find_leak` flags (correct choice by letter or text, or a right/wrong verdict on a choice) is replaced by the canned reply with `withheld: true`. This check is deterministic and limited: paraphrased leaks pass.

`llm_client.py` is the one place the SoC LLM is called. It is generic (no practice or student wording): `SoclaasClient.complete(messages, max_tokens=, caller_id=)` posts to `{SOCLAAS_BASE_URL}/chat/completions` with `Authorization: Bearer`, 15 s timeout, one retry on timeout/5xx, per-caller sliding limits of 20 per minute and 300 per day (in memory, one process), a 12,000-character input ceiling and a 2,000-character reply ceiling. Errors are `LlmError` subclasses with fixed messages; the key is never in a message, `repr` or log. Settings come from `SOCLAAS_BASE_URL`, `SOCLAAS_API_KEY` and `SOCLAAS_MODEL` (names in `src/backend/.env.example`; put real values only in an ignored `src/backend/.env`; the backend does not read that file by itself, so start it with `uv run --env-file .env uvicorn main:app --host 127.0.0.1 --port 8000 --reload` from `src/backend`, or set the variables in the shell). If any is missing the endpoint answers 503 `llm_not_configured` and makes no network call. `httpx` is a runtime dependency for this. `get_llm_client` builds the client once per process on first use: an environment change needs a restart, and a client built while unconfigured stays cached until then. The shared `practice_routes.error_response` adds a `Retry-After` header whenever `retry_after_seconds` is in the error extras. `text_normalise` holds the one normaliser shared by `question_match` and `leak_check`; the leak check also strips markdown, quote marks and Unicode format characters before matching letters.

To fake the model in tests, override the dependency: `app.dependency_overrides[llm_client.get_llm_client] = lambda: fake`, where `fake.complete(messages, *, max_tokens, caller_id)` returns an `LlmReply` or raises an `LlmError`. To test the real client, give `SoclaasClient` an `httpx.MockTransport` and a fake `clock` and `sleep`. No test or CI step reads a key or calls the real service. Live checks are run by hand with approval.

## State and preview actions

The app stores no tokens, credentials or user data in browser storage. Login fields are uncontrolled and never read by application code. Sign-in/registration display a notice. Role switching is a demonstration control, not authorisation. Form drafts and selections use local React state. Teacher Materials uploads are validated and transmitted to the private backend store; teacher note generation transmits authorised source text to the SoC LLM through the backend and persists successful drafts. Other upload/generation previews do not transmit files. Preview messages explicitly state that no save, generation, publication, access change or delivery occurs.

Practice uses single-answer MCQs only, including code-reading questions expressed as choices. The Practice page (`pages/Practice.tsx`) renders the set from `GET /api/practice-sets/intro-se-1` and keeps one session in `PracticeProvider`, mounted above the student routes so answers and results survive navigation (not reload). The attempt is created on first submit; the page then saves all answers in one PUT, submits and reads the results, each as a separate step so a retry repeats only the failed step. 422 `incomplete` shows the server's missing list, 409 loads the results, and a 404 `attempt_not_found` at the save, submit or results step makes one new attempt and repeats save, submit and results (once per submission; a second one shows "Try again"). Radios stay locked while a retry only has to finish a step after the save. The attempt id is held in memory only and nothing is written to browser storage. The page never computes correctness: score, correct choice and explanations are rendered, as text, from the results response, which the server releases only after a submit. Teacher demo questions (with answers) live in `teacherDemo.ts`, and `Teacher` and `Admin` are loaded with `React.lazy`, so the student bundles hold no answer key. Teacher Materials and draft notes use PostgreSQL; source bytes use material_file BYTEA and generation receives only the authorised selected source. Other teacher and admin screens still use placeholder data. Still to do: real authentication (SHR-01), production access integration, student persistence and lesson-aware AI context. Tests: the mocked Playwright suite needs no backend; `tests/real-backend.spec.ts` runs only when `REAL_BACKEND=1` (project `real-backend`) against a started backend, and the CI job "Real backend end-to-end" does this: `cd src/backend; uv run uvicorn main:app --port 8000`, then `cd src/frontend; REAL_BACKEND=1 npx playwright test --project=real-backend`.

## Development and verification

Continuous integration (`.github/workflows/ci.yml`) runs on every pull request into `master` and every push to it: backend tests; frontend typecheck, lint, format check, build and Playwright tests; the token tracker's and experiment scripts' unit tests; and a dependency audit that blocks on known vulnerabilities in runtime dependencies and only reports dev-only ones. It uses read-only permissions and no secrets. Plan and decisions: `workflow/specs/CI-01/plan.md`. Deployment is not built yet; options and open decisions are in `workflow/deployment.md`.

Use the startup/check commands in [README.md](../README.md). `package-lock.json` and `uv.lock` pin resolved dependencies. Local PostgreSQL credentials in the Compose file are development-only. Ignore rules exclude local env files, generated output, virtual environments, browser traces and dependency directories. Use `npm run format` to format frontend files and `npm run format:check` to check them.

Playwright exercises real UI behaviour with intercepted health responses. Backend tests independently verify the real API. Visual checks cover desktop/mobile and light/dark modes. Native form validation is used where appropriate; accessible labels, visible focus, a skip link, reduced-motion CSS and a mobile navigation drawer are included. This is not a full accessibility certification.

### TEA-01 failure and concurrency guarantees

Multipart ingestion enforces the 10 MiB limit in the parser callback before file chunks are spooled, with one file, at most two text fields, 1 KiB text parts and a total request bound of 10 MiB + 64 KiB for headers/fields. Parsed upload resources are closed on success and failure. This callback extends the installed Starlette parser; rerun chunked-ingestion regressions when upgrading FastAPI/Starlette.

Metadata and BYTEA content are flushed and metadata is serialized before one commit. Failure rolls back both; no permanent file or orphaned filesystem bytes exist. Back up/restore PostgreSQL for originals, metadata and drafts together. The 100 MiB upload budget excludes PostgreSQL overhead and other data; monitor the provider allowance. Shared extraction accepts bytes, decoding UTF-8 strictly or wrapping PDF bytes in BytesIO; sessions close before extraction/inference. Topic updates refresh their locked row so even a delayed clear-to-null writes the intended last-committed value. The UI ignores superseded course/filter requests and retries topics/materials together.

Backend `.env` is not loaded implicitly. Use `uv run --env-file .env` for Alembic, seed and Uvicorn as shown in the README. Frontend Vite loads its local `.env`; the Materials page displays whether the explicit demo identity is enabled. The CI browser-test step supplies positive demo flags without baking them into its production-build step.

## Teacher note drafts (TEA-02 notes slice)

Run `uv run --env-file .env alembic upgrade head` before starting this version. The additive revision creates `study_note_draft` and the material composite key. TEA-01's migration is frozen to its original historical schema so both fresh installs and upgrades work. See [SharedDataContract.md](SharedDataContract.md) and [TEA-02 contract](../workflow/specs/TEA-02-notes/plan.md).

The AI content studio now uses generate/list/get endpoints under `/api/teacher`. It reuses the TEA-01 development resolver/course membership checks and authorised stored bytes. Strict UTF-8 text and pypdf extraction are capped at 8,000 normalised characters/100 pages; no OCR or truncation. An unchanged `llm_client.get_llm_client` dependency supplies exactly one bounded call (`max_tokens=600`, caller `teacher:{id}`); fixed source-only context is separate from trusted instructions. No database transaction remains open during the model call. Role, membership and source are rechecked and locked before a new draft is inserted; output must be nonblank and shorter than 2,000 characters; length-finished replies and PostgreSQL-unrepresentable NUL/unpaired-surrogate output are rejected with502 llm_bad_response before persistence. Failed requests preserve sources/older drafts.

Set `SOCLAAS_BASE_URL`, `SOCLAAS_API_KEY`, `SOCLAAS_MODEL` in the ignored backend `.env`, then restart with `--env-file .env`; do not commit credentials. Existing shared per-caller limits/retries apply, with teacher caller IDs separate from student IDs. Browser generation requests use 45 seconds and no automatic retry; a response lost after commit can lead to a second draft on explicit retry (no idempotency yet). The UI renders escaped plain text and preserves line breaks. Drafts persist and remain unpublished. TEA-03 adds explicit editing below, completing the editable-notes portion of US-TEA-02-01.

Tests override the shared dependency with a fake; no provider credentials or live calls are needed. Use the existing isolated `TEA01_TEST_DATABASE_URL` schema fixture and temporary files only where needed, never the development database. The current demo header is spoofable and must be replaced before public use. PDF extraction is not process-sandboxed; stronger resource isolation belongs in a production hardening increment.


## Draft note editing (TEA-03)

Apply `uv run --env-file .env alembic upgrade head` from `src/backend` before running against an existing development database. Migration20261102_tea03 backfills immutable source_title, version1, updated_at=created_at and updated_by=created_by without changing content. Downgrade retains titles/content but drops edit metadata; re-upgrade cannot recover the earlier source snapshot after a title edit. TEA-02 merged through PR11 (`040dc07`); the user reported a successful real generation on2026-11-02. This is user-reported evidence, not an automated provider check.

PATCH `/api/teacher/note-drafts/{draft_id}` accepts exactly title, content and a strict positive integer version. It authorises the existing identity/current membership before reading the body, validates/normalises text, then locks user/membership and the current draft through commit. One concurrent version wins; stale writes return409 draft_conflict. Successful edits increment version and update server-resolved editor/time; original attribution and source/course references do not change. PostgreSQL-unrepresentable NUL/unpaired-surrogate text is422. Other invalid fields are422 validation_error and database failures503 service_unavailable. Lists retain creation-time/ID order. No editing operation calls an LLM or publishes a record.

The existing course list/get/create responses add source_title, version, updated_at and updated_by. `NoteDraftEditor` owns the local edit buffer and conflict recovery; the content studio updates persisted list/view state on successful saves. Canonical validation counts Unicode code points and matches Python whitespace trimming; raw differences still trigger unsaved warnings. The entrypoint uses a data router (wildcard App route) so useBlocker guards pathname/search/history changes without rewriting the existing route tree. Pending saves block departure; settled saves cancel any pending navigation and stay on the page. Native unload warnings cannot guarantee persistence and no local edits are stored. Automated tests use isolated schemas/files and fake generation clients, never a live model.

## Shared teacher studio lifecycle

`hooks/useTeacherStudioSources.ts` owns course/source/list loading, retry and stale-GET cleanup for both notes and MCQs; detail fetching and feature-specific editors/viewers remain separate. `hooks/useStudioGeneration.ts` owns duplicate-request prevention and a monotonic navigation/selection lifetime. Any committed navigation or source/course/draft departure permanently invalidates an outstanding success/error, including a Back/Forward round trip to the same selection; leaving the component also invalidates it. These guards suppress obsolete UI changes, not an already-running server generation.

`text_validation.is_postgres_text` shares representability checks across teacher upload titles, generated notes/MCQ fields and manual note edits. Each caller retains its own normalisation/limits and error ownership: invalid user titles/edits422, unusable generated content502. Valid Unicode including astral characters remains supported. No database migration or shared LLM-client change is needed for these corrections.
