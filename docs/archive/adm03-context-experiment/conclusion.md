# Context-management experiment: closed, adoption rejected

Closed by the user on 9 Nov 2026. The combined fresh-context/scoped-read/completion-wait policy failed its practical objective: acceptable resource use while finishing ADM-03 with the required quality gates. ADM-03 consumed **19 invocations, 1,063 model requests and 129,672,868 observed tokens**, then stopped with a blocking defect. The user chose to restore the previous workflow. **The experiment is over; ADM-03 is not complete.** Its next authorised fix is separate work under the restored workflow, with separate usage tracking. Do not extend this experiment to obtain a more favourable outcome.

This is an operational rejection of this implementation. Different features, interruptions, incomplete historical attribution and three simultaneous interventions prevent a controlled causal conclusion about fresh contexts, bounded reads or waiting individually. Token volume includes cache reads; billing and context-first/mean/max are unavailable. The recorded window includes human/idle time and bounded interrupted returns. [Frozen report](report.md), [manifest](invocations.csv), [category metrics](metrics.json), [chronology](experiment.md).

## What was wrong with context management?

**The dominant context was left in the orchestrator.** It used 329 model requests and 63,241,788 tokens, **48.77% of the run's raw token volume**. Delegated phases were fresh; the orchestrator retained the long conversation, growing evidence, bookkeeping and recovery history. The intervention did not cover its largest recorded contributor. Of the whole run, 127,116,800 tokens (98.03%) were cache reads. Raw repeated-prefix volume is not billed cost, and it does not establish that uncached context grew by the same amount. [Role/category metrics](metrics.json).

**Completion waiting did not eliminate model-driven heartbeat turns.** A scoped audit of the original root log window found **115 `wait_agent` calls: 77 timeouts, 35 completions, two interruptions and one aborted call**. Frequent short waits and progress updates continued throughout long suites. Host instructions also required frequent user updates and discouraged waits longer than 60 seconds: the proposed policy did not resolve that operational constraint. The root still made repeated decisions and wrote bookkeeping between waits. The exact tokens attributable only to waits are unavailable; all 329 root requests must not be called polling. [Aggregate audit and method](orchestration-audit.json), retired waiting policy.

**Fresh phases repeatedly paid for reconstruction.** Seven test-designer and five verifier invocations reloaded contracts, evidence and implementation context. Fresh history prevents transcript carryover but does not remove mandatory full contracts, role instructions or code reads. Short launch prose was not a measured input-context cap. Operational memory was unreliable: wrong database port U27, missing dotenv U45 and repeated missing dotenv U56 required recovery despite earlier evidence. Later packets pointing to native loaders worked; that is useful counterevidence, not proof that every fresh context causes mistakes. [Issue register](issues.md), launch policy snapshot.

**Bounded output was a guideline without effective enforcement.** Combined reads still truncated (U04 and subsequent role reports), forcing narrower rereads. Guessed paths, Windows glob failures and repeated setup discovery added turns. The orchestrator's own oversized reads and repeated reporting contributed; this was an execution failure as well as a policy-design gap. There was no measured first/mean/max context evidence showing that the intended reduction occurred. [Issues](issues.md), [measurement limitations](experiment.md).

## What was wrong with the multi-agent pipeline?

**The approved contract was not integration-ready.** The spec-writer was prohibited from inspecting implementation and explicitly flagged unverified bindings. The orchestrator did not resolve them before presenting approval. Developer-01 then stopped: the shared client retried once, limited input to 12,000 characters and truncated output to 2,000 characters, conflicting with no-retry/full strict JSON requirements. A fresh spec clarification and developer restart followed. A structural spec checker and human approval cannot certify an uninspected interface. This preflight gap belonged to the orchestration/spec pipeline; the source restriction predated this experiment. Integration gate, spec open questions, plan.

**Fixes and tests initially covered examples instead of the full lifecycle.** Explicit logout was fixed before the natural-expiry `/auth/me` cleanup path was covered. Timeout cleanup was fixed before non-timeout cleanup persistence failure was covered. A complete failure matrix needed to consider session deletion through every caller and every accepted-request transition across auth, reservation, provider, save, cleanup and replay. Passing suites did not establish that matrix. Findings arrived in successive review phases: five initial blockers, three remaining after correction one, then U63 after correction two. Initial review, correction-one review, final review.

**Resource and artifact ownership were not centrally controlled early enough.** U48 records both roles choosing port 5483, a disrupted browser run and a restart. Shared `node_modules` made executable path insufficient ownership evidence; missing pre-disruption PID/start time prevents assigning the stop to one role conclusively. U42 records a reused Playwright output directory refreshing the original failure traces. The shell timeout then remained unexplained despite 25 focused passes. These were orchestration/evidence failures, not proof of a product defect or a fresh-context effect. [Issues U42/U48](issues.md).

**Validation became expensive and fragmented.** The initial developer had five backend attempts (setup failure, two cancellations, a full run with seven temp-directory errors, then recovery), and browser regression corrections/rechecks. Later phases added full suites and long real-deadline tests. Early source edits during a browser run produced mixed-snapshot evidence (U15); that required a stable rerun. Some reruns were necessary independent checks or genuine regressions, so removing them would hide defects. Better ordering was needed: resolve environment/integration facts and comprehensive targeted failure cases before broad runs; preserve exact stable-tree evidence and avoid duplicate executions. Recovery eventually reused the surviving final backend process correctly, rather than restarting it. Developer handoff, [issues U11-U22](issues.md), [final recovered results](report.md).

**Quotas and phase fragmentation amplified overhead.** Three provider-limit interruptions produced recovery contexts, timing bounds and report work. The manifest shows five verifier starts and seven test-designer starts; the final reviewer was stopped at the two-round cap. The original workflow also requires independent tests/review, and ADM-04 also had interruptions. Their existence is not caused solely by this policy. Mandatory fresh phase launches, repeated reconstruction and the orchestrator's handling made the observed run more fragmented; the exact marginal token cost of each cause is unavailable. [Invocation ledger](invocations.csv), [chronology](experiment.md).

## What worked, and the decision

Independent tests and security review were valuable. The final reviewer refused to infer safety from 1,612/817 green standard tests and demonstrated U63: terminal 502, immediate pending 409, one provider call. Preserving that finding and stopping at the cap was correct. Retain the approved-spec gate, independent test worktree, server-side safeguards, security review, revision cap, usage reporting and existing evidence. The failure was expensive orchestration and incomplete lifecycle planning/implementation; security detection is not something to remove to obtain a green status.

**Decision: close this pilot as a practical failure and restore the previous Variant B workflow.** Remove the experiment's mandatory fresh-phase/launch/read/wait policy and associated active references in a separate local commit. Preserve its historical policy snapshots, all measurements/reviews/issues, and ADM-03 code/tests. Future ADM-03 repair uses the restored workflow and a new usage run; it must carry forward U63 and prior correction history, not silently reset that history. This request does not apply the U63 fix. Rollback itself does not guarantee lower future tokens or isolate a cause.

This postmortem/rollback is separately tracked as CONTEXT-CLOSE-01. Its administrative resource use is excluded from the frozen ADM-03 feature totals. No application tests or fixes were run for this closure.
