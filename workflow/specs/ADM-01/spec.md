# Spec: ADM-01 Feature analytics

Status: Approved (2026-11-09). The human approved all 12 open questions below as drafted, with no overrides.

## Goal
An admin can pick a reporting period and review (1) chatbot outcomes and practice-set completion, (2) generation success rates per AI content-generation workflow, and (3) advisory AI quality grades, response timing, session message counts and linked activity durations, with explicit "unavailable" and "not applicable" states and without showing private conversation content (US-ADM-01-01, US-ADM-01-02, US-ADM-01-03).

## Behaviour

### Where it lives
- New admin-only screen at `/admin/analytics`, reached from an "Analytics" link in the admin navigation.
- New backend module `src/backend/feature_analytics/`, with admin-only routes under `/api/admin/analytics` (contract in `plan.md`).
- Nothing is recorded today, so the feature adds **recording hooks**: small functions called from the existing student companion (chatbot), practice-attempt and TEA-02 generation routes. They write rows to analytics tables owned by this module. A recording failure never changes the user's response (AC2).
- Counts, rates and timings come from those tables, not from the private chat content. Reports show counts and grades, never conversation text.

### Reporting period
- A period is two UTC calendar dates, "From date" and "To date", both inclusive: from `From 00:00:00 UTC` up to but excluding `To + 1 day 00:00:00 UTC`.
- Default when the page opens with no valid period in the URL: the last 30 days, ending today (UTC).
- Maximum 366 days. "From date" must be on or before "To date". The selected period and workflow are kept in the URL query (`?from=YYYY-MM-DD&to=YYYY-MM-DD&workflow=student_exercise|teacher_lesson_planning`).
- Recording starts when this feature is deployed. If the period starts before the recording start date, every metric that needs recorded data is labelled unavailable (AC12). There is no backfill (open question 3).

### Panel 1: Feature usage (US-ADM-01-01)
- **Chatbot requests**, for the selected period: for students and for teachers separately, one row per user with at least one request (name, successful count, unsuccessful count), a role subtotal, and a grand total for both roles.
  - Successful: the chatbot returned a valid response message. Unsuccessful: any error, rate-limit, timeout or missing response (open question 4).
- **Practice-set completion**: attempts started in the period, how many of those were submitted (whole set, successfully) by the end of the period, and the percentage. If no attempts were started, show "Not applicable", never a percentage.
- Zero is shown as `0` when data is available; "Unavailable" with a reason when the value cannot be read reliably.
- Teacher chatbot data: no teacher chatbot exists to record, so the teacher group and the grand total are shown "Unavailable" with a reason (open question 1).

### Panel 2: Generation reliability (US-ADM-01-02)
- A table with one row per workflow, always both rows, in this order: **Study notes** (`study_notes`) and **MCQ batches** (`mcq_batch`), TEA-02 workflows. Each row shows attempts, successful, unsuccessful and success rate for the selected period; the page heading of the panel and the period fields identify the period for every rate.
- An attempt is counted when a valid request is accepted for generation: after authorisation, validation, rate limit and source loading have passed, immediately before the AI generation call starts. Anything rejected earlier is not an attempt (open question 9).
- Successful only when a complete output in the expected format is returned. Errors, timeouts, incomplete or invalid outputs, and attempts that never got an outcome recorded, are unsuccessful.
- Rate = successful / attempts. With no attempts: "No rate can be calculated", never a percentage.

### Panel 3: AI quality and session activity (US-ADM-01-03)
- Tabs select the assessment workflow: **Student exercises** (companion replies to requests made during a practice attempt) and **Teacher lesson planning** (TEA-02 generated notes and MCQ batches). Results are always shown for one workflow at a time, with the workflow and period named in the panel.
- Always shown at the top of the panel: "Grades are AI assessments, not verified facts. They do not change access or application content."
- **Quality grades**: an admin starts grading with the button "Grade ungraded responses" (confirmation first). A grading run sends up to 20 ungraded responses from the selected workflow and period, one at a time, to the SoC LLM service through the shared client. Each response is graded on relevance, factual accuracy, clarity and safety, 1 to 5 (1 unacceptable, 2 major shortcomings, 3 adequate with notable shortcomings, 4 good with minor shortcomings, 5 excellent), each with a short reason. A dimension that cannot be assessed is "Unassessable", not graded. The panel shows the average per dimension (graded responses only), counts of assessed, waiting and failed responses, and a paginated table of assessed responses with grades and reasons.
- **Response time**: per assessed response, elapsed time from request receipt to final response; plus the mean and median over successful responses. Failed or incomplete requests are counted separately and their elapsed time is never shown as a response time.
- **Session activity** (student exercises only): for sessions that began in the period, the number of sessions and the average messages per session (user and AI messages counted separately, total divided by sessions).
- **Associated activity time** (student exercises only): for sessions linked to a practice attempt that has recorded start and end events, the average messages per session next to the average elapsed time from "Practice attempt started" to "Practice attempt submitted", plus linked sessions, distinct activities, and the number of sessions excluded because the activity has no recorded end. Elapsed time includes idle time.
- Teacher lesson planning has no conversation sessions recorded, so session activity and associated activity time are "Unavailable" there (open question 1).
- Timing and message counts are labelled as descriptive measurements, not quality grades or evidence of time saved. No comparison with a no-AI baseline.

### Grading rules
- Only successful, completed responses are assessable. Each is graded once; failed items can be retried by a later run.
- The grader sees only a bounded, redacted copy of the request, the response and, if there is one, the authorised context stored when the response was produced. It never receives answer keys, solutions, explanations of correct answers, credentials, names or user identifiers (AC23).
- Stored text is removed as soon as the response is graded, and at the latest 7 days after it was recorded (open question 5). No API returns it.
- A run is asynchronous: the admin sees progress, can leave and return, and only one run can be active at a time.

## Acceptance criteria
Stories are cited as US-ADM-01-0x. Criteria copied from the stories are marked "(story)"; the rest make the story testable.

### Access and platform
- [ ] AC1 Every `/api/admin/analytics/*` endpoint rejects an unauthenticated request (401) and a student or teacher (403) using the shared authentication behaviour; an admin succeeds. All responses carry `Cache-Control: no-store`.
- [ ] AC2 Recording hooks never raise and never change the host route's status code or body, even when the analytics tables are unavailable; a failed write is logged without request content.
- [ ] AC3 The period validates as specified in `plan.md` (dates strictly `YYYY-MM-DD` after trimming, From ≤ To, at most 366 days); each invalid input returns 422 with its exact code and message from `plan.md`.

### US-ADM-01-01 Feature usage
- [ ] AC4 (story) A chatbot request is successful only when it returned a valid response message; an error or missing response is non-successful, including a request that never received an outcome.
- [ ] AC5 (story) For the period, the report gives, for each role, every user's successful and non-successful counts, the role totals, and the totals for each outcome across both roles.
- [ ] AC6 Requests are counted by `received_at` inside the period (From 00:00:00 UTC inclusive, To + 1 day 00:00:00 UTC exclusive). A request just before or after the boundary is excluded.
- [ ] AC7 Only users with at least one request in the period get a row. A role with data available and no requests shows totals of 0 and no rows.
- [ ] AC8 (story) A started practice attempt is complete only when the whole set was successfully submitted. For attempts started in the period, completion percentage = attempts submitted before the end of the period ÷ attempts started in the period, rounded to one decimal.
- [ ] AC9 An attempt started before the period is not counted; an attempt started in the period and submitted after the period end is counted as started but not complete.
- [ ] AC10 (story) If no attempt was started in the period, completion is `not_applicable` with no percentage.
- [ ] AC11 (story) The usage response and screen contain no chat message text, no prompt or reply text, and no AI call totals, failure categories or resource measurements.
- [ ] AC12 (story) A metric whose data cannot be read reliably is `unavailable` with a reason, never `0`. This covers a period starting before the recording start date and a failed read of one metric (the other metrics are still returned).
- [ ] AC13 Teacher chatbot counts and the grand total are `unavailable` (reason `no_source`) while no teacher chatbot is recorded.

### US-ADM-01-02 Generation reliability
- [ ] AC14 (story) The response identifies the workflow and period for every rate, and always contains both workflows (`study_notes`, `mcq_batch`).
- [ ] AC15 (story) A generation attempt is recorded when a valid request is accepted for generation, immediately before the AI call. Requests rejected earlier (401, 403, 404, 413, 422, 429, source could not be read) create no attempt.
- [ ] AC16 (story) An attempt is successful only with a complete output in the expected format. Errors, timeouts, incomplete or invalid outputs, and attempts with no outcome are unsuccessful. Every code path after the attempt is recorded, including an exception, records exactly one outcome.
- [ ] AC17 (story) Rate = successful ÷ all attempts in that workflow and period, as a percentage rounded to one decimal.
- [ ] AC18 (story) With no attempts, the row is `not_applicable` with no rate.
- [ ] AC19 (story) The generation response contains no chatbot outcomes and no AI service-call or failure-category counts.

### US-ADM-01-03 AI quality and session activity
- [ ] AC20 (story) The admin selects a period and a workflow (`student_exercise`, `teacher_lesson_planning`); the response and screen name the workflow and the period, and list only individual successful responses to requests received in that period.
- [ ] AC21 (story) A grading run grades each selected response on relevance, factual accuracy, clarity and safety. Each dimension has an integer score 1 to 5 or is `unassessable` with no score, and each has a reason of 1 to 300 characters.
- [ ] AC22 (story) The reason is grounded in the response and context but does not quote private content: a reason that contains any 30 or more consecutive characters (case-insensitive, whitespace collapsed) copied from the stored request, response or context is rejected and the item is `grading_failed`.
- [ ] AC23 (story) The grader input excludes credentials, email addresses, long token-like strings, names and user identifiers, and answer keys, correct-answer markers and solution explanations. Stored and graded content is treated as untrusted: it is placed in labelled data blocks and the model's output is validated against a fixed schema; invalid output is rejected and nothing from it is stored.
- [ ] AC24 Factual accuracy is forced to `unassessable` by the server (not the prompt) when the item has no authorised context, and for every `mcq_batch` item.
- [ ] AC25 (story) Grades are advisory: grading changes only analytics rows; no other table, access rule or content changes. The screen states this.
- [ ] AC26 (story) For each assessed response, the elapsed time from request receipt to final response is shown. Failed or incomplete requests are counted separately (`failed_or_incomplete_count`) and carry no response time. Mean and median use successful responses only.
- [ ] AC27 (story) For student-exercise sessions that began in the period, the response gives the number of sessions and the average number of messages per session (user messages plus AI messages, each counted separately, total ÷ sessions). A session starts at the first message linked to a practice attempt and ends when the attempt is submitted, when the user sends a message for a different attempt, or after 30 minutes without a message, whichever comes first (open question 7).
- [ ] AC28 (story) The associated activity time shows the average messages per session next to the average elapsed time from the recorded attempt start to the recorded attempt submission for each distinct attempt, with the number of linked sessions and distinct activities used, and the names of the start and end events. Elapsed time includes idle time and is labelled so.
- [ ] AC29 (story) Sessions whose attempt has no recorded start or end are excluded from that comparison and their number is shown.
- [ ] AC30 (story) A metric with missing or incomplete measurements is `unavailable`; with no eligible records it is `not_applicable` ("no average can be calculated").
- [ ] AC31 Teacher lesson planning session activity and associated activity time are `unavailable` (reason `no_source`); its grades and response time are available.
- [ ] AC32 (story) Timing and message counts are labelled descriptive measurements; the screen never shows them as quality grades or as time saved, and shows no no-AI comparison.
- [ ] AC33 Starting grading: valid request returns 202 with a run; a second request while a run is queued or running returns 409; more than 10 runs started in a rolling hour returns 429; invalid workflow or period returns 422.
- [ ] AC34 A run selects at most 20 items: status pending or `grading_failed`, content still stored, in the chosen workflow and period, newest first. It calls the AI once per item, never more than once per item per run, and does not retry on AI failure.
- [ ] AC35 When the AI is rate-limited, times out or is unavailable, the run stops with its failure code; graded items stay graded and the rest stay pending. Invalid output for one item marks only that item `grading_failed` and the run continues.
- [ ] AC36 No AI call starts more than 600 seconds after the run starts. A run left `queued` or `running` for more than 900 seconds is reported as failed with `run_expired`.
- [ ] AC37 After an item is graded its stored request, response and context text are deleted. Items still ungraded 7 days after they were recorded are reported as `content_expired`, their text is deleted by the next run start, and they are never sent to the AI.

### Concurrency and isolation
- [ ] AC38 Two simultaneous grading starts give exactly one 202 and one 409; two simultaneous `record_practice_attempt_started` calls for one attempt give one row; two simultaneous first chat messages by one user create one open session.
- [ ] AC39 Recording hooks write the real user's id from the authenticated session only; no admin endpoint accepts a user id for filtering or reading another source.

### Screen (US-ADM-01-01 to 03)
- [ ] AC40 An admin at `/admin/analytics` sees the title, the period panel and three panels, and loads them with three requests (usage, generation, quality) as specified in "UI states and copy". Each panel shows its own loading, success, empty and failure states; one failed panel does not hide the others.
- [ ] AC41 Invalid period input is rejected in the page with the exact messages, with no request, the typed values kept and focus on the first invalid field.
- [ ] AC42 "Apply period" and the workflow tabs update the URL and reload only what changed; Back, Forward and Refresh restore the period and workflow from the URL.
- [ ] AC43 The grading dialog, progress, completion and each failure state use the exact copy below; a failed start keeps the results and the period.
- [ ] AC44 A student or teacher, or an anonymous visitor, never sees analytics data and no analytics request is sent from the page; an expired session or logout ends at the sign-in page with no analytics data left on screen.
- [ ] AC45 Controls are keyboard operable with the roles and names in `plan.md`; no horizontal page scrolling at 320 to 390 px; both themes keep outlines and contrast; reduced motion is respected.

## Out of scope
- AI service-call counts, retries, rate-limit or failure categories, and token or resource measurements (ADM-06). Token use of grading calls is recorded by the shared client for ADM-06 under the feature label `ADM-01`; this feature does not display it.
- Showing, searching or exporting chat messages, prompts, replies or generated content; any drill-down into a conversation.
- A teacher chatbot or teacher conversation sessions (not recorded; shown unavailable).
- Backfilling analytics from data that predates this feature; lesson-mode or general chat quality grades (counted in chatbot usage, not graded).
- Automatic or scheduled grading; grading by anyone but an admin; changing access, content or accounts from a grade.
- Comparison with a no-AI baseline; charts, CSV export, dashboards for students or teachers; per-user filters.
- Time-zone selection (UTC only).

## Security and AI safeguards
- Access: only admins use `/api/admin/analytics/*` and the `/admin/analytics` screen (shared admin authentication pattern, server-side). No endpoint accepts a user id, course id or record id from the client other than the grading run id (admin-only).
- Private data: analytics rows hold counts, timestamps and ids; user text is stored only for the grading step (bounded, redacted, deleted after grading or after 7 days) and is never returned by any endpoint or logged. Names shown are account display names for users with requests.
- Answer protection (SHR-02): grading input is built only from text already released to the student or teacher, with answer keys, correct-answer markers and explanations excluded. For MCQ batches only question stems and choices are passed, using a helper that has no parameter for keys or explanations. Factual accuracy for MCQ batches is forced unassessable.
- Untrusted input and output: stored requests, responses and context are untrusted; they are placed in delimited data blocks, the model has no tools, the output is validated against a fixed schema (four dimensions, integer 1 to 5 or unassessable, reason 1 to 300 characters, no extra fields), and a reason that copies 30 or more consecutive characters is rejected. Access is enforced by the server and never by the prompt.
- AI services receive no credentials, names, user ids or email addresses.
- Limits and quotas (SHR-03): at most 20 items per run; one active run at a time; at most 10 runs started per rolling hour across admins; one AI call per item per run, no automatic retry; each call bounded by the shared client's timeout; no call starts after 600 seconds; stored text capped at 2,000 characters for the request, 6,000 for the response and 3,000 for the context; the period is at most 366 days; page size at most 100; user rows capped at 500 per role (`rows_truncated` flag).
- Recording hooks are best-effort and isolated: they use their own short database session, swallow and log their own errors, and cannot change the host route's outcome.
- Safe rendering: all names, reasons and values are rendered as plain text.
- Concurrent requests (same time): only one grading run can be queued or running (database-enforced, one 202 and the rest 409); attempt-start and attempt-submit hooks are idempotent per attempt reference; at most one open session per user (database-enforced), so two simultaneous first messages give one session; a grade for an item and dimension is stored once.
- Normalisation: dates are trimmed and must be exactly `YYYY-MM-DD`; `workflow` is trimmed and compared exactly in lower case (`student_exercise`, `teacher_lesson_planning`); `activity_ref` and `attempt_ref` are trimmed strings of at most 100 characters; stored text is trimmed and has runs of whitespace kept as written before redaction.

## Open questions
Each item shows the proposed default. The human can accept all or override. Items 1, 3, 5, 6 and 10 affect privacy, retention or quotas; the "Decisions to resolve before implementation" entry "Exact SoC LLM quotas, model configuration and resource measurements available to the app" affects item 10, and the retention decisions affect item 5.

1. **Teacher side.** No teacher chatbot exists, and TEA-02 generation is the only teacher AI. Default: teacher chatbot counts, the grand total, teacher sessions and teacher activity time are "Unavailable: this activity is not recorded"; "teacher lesson-planning assistance" for grades and response time means TEA-02 study notes and MCQ batches. Alternative: define teacher counts from TEA-02 generation requests, which would blur the ADM-01-01 and ADM-01-02 boundary.
2. **Period definition.** Default: UTC calendar dates, both inclusive, maximum 366 days, default last 30 days, no presets.
3. **Data before recording started.** Default: no backfill; a period starting before the recording start date shows affected metrics as unavailable with the recording date. Alternative: backfill practice attempts from the existing STU-02 tables (more work, since practice data may already exist).
4. **Which chatbot requests count.** Default: a request is recorded after authentication, validation and the companion's own checks pass, when it reaches the chatbot. Replies that follow the companion's rules (for example a hint-only refusal) are successful; rate-limited, timed-out, upstream-error and no-response requests are non-successful; requests rejected earlier (401, 403, 422) are not recorded. Student requests of every mode (lessons, practice, general) count in the usage totals.
5. **Stored text for grading and retention.** Chat history is not kept server-side today, so grading needs a copy. Default: store a bounded, redacted copy (2,000 / 6,000 / 3,000 characters for request / response / context) for each successful response; delete it as soon as it is graded or after 7 days; never return it. Alternative: sample only some responses, or do not offer grading. This touches the open "retention and deletion" decision.
6. **What is graded and how.** Default: student exercise assessment covers only companion replies made during a practice attempt; grading is started by an admin ("Grade ungraded responses"), at most 20 responses per run, newest first, one run at a time, at most 10 runs per rolling hour, no automatic retry; failed items are retried by a later run.
7. **Session boundary.** Chat history is browser-only, so "user starts a new conversation" is not visible to the server. Default: server-derived sessions per user and practice attempt; a session ends when the attempt is submitted, when a message for a different attempt arrives, or after 30 minutes without a message. Alternative: add a conversation id sent by the client (changes the companion request).
8. **Activity start and end events.** Default: for student exercises, "Practice attempt started" and "Practice attempt submitted" (successful whole-set submission); an attempt not yet submitted has no end and its sessions are excluded and counted. Teacher activity time is unavailable (item 1).
9. **Measurement boundaries.** Default: a chat request is recorded when it reaches the chatbot (after authentication, validation and rate limit); a generation attempt is recorded immediately before the AI call, after validation, rate limit and source loading; response time is measured on the server from that point to the final response and excludes network and browser time. A source file that cannot be read is therefore a pre-generation rejection, not an attempt.
10. **Model and quotas for grading.** Default: use the shared SoC LLM client with the default model configuration used by ADM-03; the quotas in item 6 are placeholders until the SoC quotas are decided.
11. **MCQ answer protection.** Default: MCQ batches are graded on question stems and choices only; the correct choice and explanation are never stored or sent; factual accuracy is unassessable for them.
12. **Per-user rows.** Default: show display name (not email) and only users with at least one request, capped at 500 rows per role with a "rows truncated" note, totals computed over all users; no search or paging.
