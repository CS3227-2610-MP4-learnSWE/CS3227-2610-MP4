# Spec: STU-02 Practice on teacher-published sets

Status: Approved by the user on 2026-11-06 (six decisions under "Decisions (user)", the recommended answers to open questions 1 to 11, and question 12 resolved as 422 on every set-id route). Built and verified locally on 2026-11-06 (verifier PASS in round 2). Open question 5 (question reuse and an attempt cap) and the `parse_uuid` leniency noted in the notes stay undecided.

## Goal
From the user stories: a student answers and submits a published practice set so that they can check their understanding (US-STU-02-01), and reviews a saved attempt after submission (US-STU-02-02). Until now the practice flow ran on one code fixture set (`intro-se-1`). This feature makes the same flow run on the practice sets that teachers publish (TEA-03), restricted to the courses the student belongs to, and lets the student pick which set to practise.

## Behaviour
- One source of sets: a set provider (`set_provider.py`) looks a practice set up by id for one student. It returns a set only when it is a published set (`published_practice_set`) in a course where the student has a membership row. It is backed by the database. The code fixture set is removed from the product; it survives only as a test fake. The provider is the single place that decides which published sets a student can see and read: the practice endpoints, the picker, the companion lookup, progress and the two TEA-03 student routes (`GET /api/study/courses/{course_id}/practice-sets`, `GET /api/study/practice-sets/{set_id}`) all call it, so there is no second copy of the membership query. Those two TEA-03 routes keep their URLs, response shapes, status codes and error codes exactly as today.
- Every practice endpoint uses the provider: read set, start attempt, read attempt, save answers, submit, results. A set id taken from the URL (read set, start attempt, companion `set_id`) is first parsed with the TEA-03 `parse_uuid`: a value that is not a UUID gives 422 `validation_error` "A valid UUID is required." exactly as on the TEA-03 routes (decided: practice endpoints and TEA-03 routes agree). A valid UUID that matches no published set, a set in a course the student is not (or no longer) a member of, and an attempt whose set cannot be resolved for the student all give the same 404 `set_not_found` with the same body. This matches how lessons treat non-members.
- Set ids are UUID strings. Question ids are the published snapshot question ids (UUID strings). Choice ids are `a`, `b`, `c`, `d`, in the stored order of the four choices (first choice is `a`). The correct choice is the stored `correct_choice_index` mapped the same way. `code` is always null (published questions have plain text only). The key version of every published set is `v1` (published snapshots never change).
- New student page "Practice set picker" at `/student/practice`: a plain list grouped by course (courses A to Z by title), sets newest first inside each course. Each row shows the set title (a link), its topic name and the student's best score on it if any ("Best score: C / T") or "No attempts yet". One new endpoint, `GET /api/practice-sets`, returns everything the picker needs in one request. It adds to the provider's catalog only what TEA-03 lacks: grouping by member course and the student's best score per set from attempts; it does not run its own query for sets.
- Opening a set goes to `/student/practice/SETID` (the URL carries the set id; the hard-coded `PRACTICE_SET_ID` is removed). That page is the existing practice page (questions, whole-set submission, results, "Start another attempt") with the set read from the URL. New failure states exist for a set that is not available (404). Nothing else on that page changes, except that the hard-coded "SOFTWARE ENGINEERING ESSENTIALS" tag is removed because the page no longer knows a fixed subject.
- Retakes are unlimited. Each attempt is independent. The picker and the Progress page show the best score and the latest score (STU-04 behaviour, unchanged). Known limit (decision 5): answers are visible after submission, so repeated attempts on the same questions can raise a score; question reuse after answers have been seen, and a cap on attempts, are still undecided (listed decision "Repeat-attempt scoring, question reuse after answers have been seen"). This feature does not solve it.
- Progress (STU-04): `GET /api/progress` resolves sets through the provider, restricted to the student's courses. Attempts on a set that cannot be resolved (the old `intro-se-1`, a set in a course the student left) are skipped, as STU-04 already skips sets that no longer exist. The weak-topic rule is unchanged (at least 3 answers and under 60% on the latest submitted attempt per set). A published set has exactly one topic, so progress uses the set's topic for all of its questions.
- Study companion (STU-03): only its set lookup changes. It resolves the context set, the pasted-question match set and the leak-check scope through the same provider, with the same access rules (a set the student cannot access gives 404 `set_not_found` before any model call). Prompts, hint quality, modes, limits, rate limits and lesson grounding are not touched (separate later STU-03 run).
- Dev data: a development-only seed creates one published set, with the teacher draft rows its restrictive foreign keys need, so a local database and the CI real-backend job have a set to practise. It is idempotent and refuses to run unless `APP_ENV` is `development`.
- No migration is needed: `practice_attempt.set_id` is `varchar(64)` and holds a 36-character UUID. Old attempts on `intro-se-1` are development data and stay in the table unused.
- No AI call is added. The set read response never contains a correct choice or an explanation.

## Acceptance criteria
AC1 to AC8 are copied from the user stories (US-STU-02-01, US-STU-02-02), restated for published sets. AC9 onward are derived from the user's decisions, STU-03, STU-04 and the shared acceptance criteria (SHR-01, SHR-02, SHR-05); derived ones are marked.

- [ ] AC1 (US-STU-02-01): I complete all single-answer multiple-choice questions (MCQs), then submit the whole set in one action; incomplete sets are rejected with the missing questions identified. This holds for a teacher-published set.
- [ ] AC2 (US-STU-02-01): Every question supplies choices with exactly one correct answer; I select one choice per question. Code snippets may appear in a question, but there is no free-text answer input.
- [ ] AC3 (US-STU-02-01): I can revise answers before whole-set submission; there is no per-question submission, score or immediate correctness feedback.
- [ ] AC4 (US-STU-02-01): Successful submission saves the complete attempt, answers and set score against the question and answer-key version used, then makes results available.
- [ ] AC5 (US-STU-02-01): Failed submission does not unlock results or full AI solutions and preserves my entered answers for retry.
- [ ] AC6 (US-STU-02-02): Only after successful whole-set submission can I see my submitted answers, set score, correct answers and teacher-approved explanations.
- [ ] AC7 (US-STU-02-02): Direct requests cannot retrieve answer keys or solution explanations for an unsubmitted attempt. This includes `GET /api/practice-sets/SETID`, whose body for a published set contains no correct choice, no correct index and no explanation.
- [ ] AC8 (US-STU-02-02): I cannot retrieve another student's private attempts.
- [ ] AC9 (derived, decision 1, SHR-01): The set provider returns a set only if it is a published practice set in a course where the student has a membership. The fixture set `intro-se-1` is not served by any endpoint: `GET /api/practice-sets/intro-se-1` is 422 `validation_error` (it is not a UUID).
- [ ] AC10 (derived, decision 3, SHR-01, SHR-05): For a student who is not (or no longer) a member of the set's course, every practice endpoint gives 404 `set_not_found` with the identical body as for an unknown set id: read set, start attempt, read attempt, save answers, submit and results. Status, `detail.code` and `detail.message` do not differ between a valid UUID that is unknown and one that belongs to a course the student is not in. (A malformed set id is a different, 422 case: AC11.) The attempt endpoints take no set id from the client; an attempt whose stored set id is not resolvable (for example an old `intro-se-1` attempt) gives 404 `set_not_found`.
- [ ] AC11 (derived, decision 3, decided 2026-11-06): A set id in the path of `GET /api/practice-sets/{set_id}` or `POST /api/practice-sets/{set_id}/attempts`, or a `set_id` in the companion context without an attempt, is parsed with the TEA-03 `parse_uuid` (`UUID(value)`). A value that does not parse (for example `intro-se-1`, an empty-looking or very long value, text with spaces, a value with a NUL byte or other control characters, a SQL-looking string) gives 422 `validation_error` with the message "A valid UUID is required.", never 500, and the database is not queried with it. A value that parses is normalised to the lowercase hyphenated form, so an uppercase spelling, braces or no hyphens of a real set id find that same set (404 rules of AC10 apply). A path with an encoded slash is not routed and gives FastAPI's own 404. Check order: 401, 403, then 422, then 404.
- [ ] AC12 (derived, decision 3): Role gate: no session gives 401 `unauthenticated`; a teacher or admin session gives 403 `forbidden` on every practice endpoint and on `GET /api/practice-sets`, including for a published set of the teacher's own course. No identity header or query parameter is read.
- [ ] AC13 (derived, mapping): For a published set, the read response lists the questions in stored position order with the snapshot question ids, `code` null, and four choices with ids `a`, `b`, `c`, `d` in stored order; scoring and results use the stored `correct_choice_index` with the same mapping (index 0 is `a`, index 3 is `d`). Answers outside `a` to `d`, uppercase letters and unknown question ids are 422 `invalid_choice` and `unknown_question` as before.
- [ ] AC14 (derived, picker, decision 2): `GET /api/practice-sets`, built on the provider's catalog, returns the student's member courses (A to Z by title, then id), each with its published sets (newest first), each set with its id, title, topic id and name, publication time, question count and `best` (the student's best submitted score on it, or null). It contains only the caller's own best scores, no answer data, and no set from a course the student is not in. A member course with no sets appears with an empty list.
- [ ] AC15 (derived, picker UI): The picker page shows every state in "UI states and copy" with the exact messages and accessible names in the plan's UI contract. No failure shows a raw body, stack trace or HTTP code.
- [ ] AC16 (derived, set page UI): The practice page reads the set id from the URL (`/student/practice/SETID`), shows the new not-available states with the exact messages, keeps every existing practice state and message, and never shows a set, answers or results from a set the server refused.
- [ ] AC17 (derived, membership removed mid-attempt): If a student's membership is removed after an attempt was started, the next request of every attempt endpoint (read, save, submit, results) is 404 `set_not_found`; no answer, score or explanation is released by it; submitted results of that attempt are no longer readable. If the membership is restored, the same attempt works again. A request already past the access check when the membership is removed may complete once; no later request does.
- [ ] AC18 (derived, set removed): If the set cannot be resolved any more (deleted at the database level, which the application does not do), attempt endpoints give 404 `set_not_found`, the stored attempt is not changed, and progress skips the set. Nothing returns 500.
- [ ] AC19 (derived, decision 4, STU-03): The study companion resolves its set context through the provider. A `set_id` or an attempt on a set the student cannot access gives 404 `set_not_found` with no model call; a `set_id` that is not a UUID gives 422 `validation_error` "A valid UUID is required." (parsed only when the context has no attempt id, after the attempt lookup and consistency check, before the set lookup; no model call). Before submission the companion context still contains no answer key and no explanation; the hint/explain mode selection, check order (attempt lookup, then consistency 422, then set lookup), prompts and leak check are unchanged. The pasted-question match and the leak-check scope cover only sets the student can access.
- [ ] AC20 (derived, decision 6, STU-04): `GET /api/progress` lists practice scores and topics only for sets the student can access. A published set's questions are all reported under the set's topic name; the weak-topic rule and the figures for the other sections are unchanged. Old `intro-se-1` attempts do not appear and do not cause an error.
- [ ] AC21 (derived, decision 5): A student can start and submit the same published set any number of times; each submitted attempt is counted, the picker shows the best score, and the Progress page shows best, latest and the number of submitted attempts.
- [ ] AC22 (derived, concurrency): Two simultaneous submissions of one attempt give one 200 and one 409 `already_submitted`. Simultaneous answer saves on different questions lose nothing. Simultaneous attempt starts by several students on one set create independent attempts. A membership change racing a request gives only 200 (request passed the check first) or 404, never a 500 or a half-saved attempt.
- [ ] AC23 (derived, dev seed): `python -m teacher_publications.seed` creates exactly one published set with three questions, plus the material, draft batch and three draft questions its foreign keys need, only when `APP_ENV` is `development`; running it twice changes nothing the second time; it never overwrites an existing row; with any other `APP_ENV` it creates nothing and exits with a non-zero code.
- [ ] AC24 (derived, no migration): No Alembic revision is added. The single head stays `20261105_stu04_practice_attempt`. A UUID set id can be stored in `practice_attempt.set_id`.
- [ ] AC25 (derived, regression): The existing backend and Playwright suites pass. Tests that name `intro-se-1`, import the fixture from `practice_data`, or rely on the hard-coded set id are rewritten against published sets (test fake provider or database rows), not deleted.
- [ ] AC27 (derived, one access rule, TEA-03 unchanged): `GET /api/study/courses/{course_id}/practice-sets` and `GET /api/study/practice-sets/{set_id}` now call the provider and keep their URLs, response shapes, status codes, error codes, messages, ordering and `Cache-Control: no-store` exactly as in TEA-03 (the existing TEA-03 tests for them pass unchanged). For any student and any set, the TEA-03 routes, `GET /api/practice-sets`, `GET /api/practice-sets/{set_id}` and the attempt endpoints agree: a set is listed or readable by one only if it is by all (same membership, including after a membership is removed or restored). The answer-free set body of `GET /api/study/practice-sets/{set_id}` equals the body of `GET /api/practice-sets/{set_id}` for the same set.
- [ ] AC26 (derived, docs): `docs/UserGuide.md`, `docs/DeveloperGuide.md`, `docs/SharedDataContract.md` and `workflow/security/test-log.md` describe what works and no more, including the seed command and the known repeat-attempt limit.

- Requests per load and per retry: the picker sends exactly one `GET /api/practice-sets` on load and one per "Try again", and no other API request (no `/api/study/courses`, no `/api/progress`). The practice page sends exactly one `GET /api/practice-sets/SETID` on load and one per "Try again" (for a set whose state is already held, see Back and Forward). Development builds run effects twice, so identical in-flight GET requests are shared and never duplicated.
- Wrong role: a teacher or admin who opens `/student/practice` or `/student/practice/SETID` is redirected by the SHR-01 role guard to their own area (`/teacher/overview`, `/admin/overview`) before any request is sent; the 403 message appears only if the role changes after load; in demo mode (anonymous) the pages request the endpoint, get 401 and show the sign-in notice.
- Link history: push or replace: the sidebar link "Practice", every set link, "Back to practice sets", "Go to sign in" and the Progress page link "Go to practice" push a new history entry; nothing in this feature replaces an entry; "Try again" and "Start another attempt" do not change the URL. The 401 return to `/login` while signed in is done by the existing auth hook, unchanged.
- Refresh: the picker reloads from the server (loading status, then the list). The practice page reloads the set from the server: chosen answers and the in-memory attempt id are lost (attempts already started stay stored as in progress), and the page shows the loading status and then a fresh empty form. An old bookmark such as `/student/practice/intro-se-1` gets 422 from the server and shows "This practice set is not available to you." (the same message as for a 404).
- Back and Forward: the picker holds no cache, so Back or Forward to it sends one request and shows the current list and best scores. The practice page keeps the state of the one set last opened in this browser tab session (chosen answers, results), so Back or Forward to that same set id shows it again without a new request; opening a different set id resets that state and loads the new set (one request). Scroll position is not specified.
- Expired session or logout: protected data is not shown; signed-in users go to `/login`; demo mode shows the sign-in notice (picker: "Sign in to see your practice sets."; practice page: its existing notice). - Backend down: the picker shows "Could not reach the server. Check your connection and try again." with "Try again"; the practice page shows "We could not load the practice set. Please try again." with "Try again"; recovery needs no page reload.
- Longest wait before an error: 10 s per request (`REQUEST_TIMEOUT_MS`); each screen's load is one request, so an error appears at most 10 s after the page opens or after "Try again". Submission steps keep their existing 10 s each. There is no hidden longer wait.

## Out of scope
- Companion prompts, hint quality, lesson grounding, source references, quotas and models (separate later STU-03 run). Only the set lookup changes, as stated above.
- Teacher publishing, withdrawing or editing published sets (TEA-03, TEA-04) and any student-facing "unpublish". Published snapshots are immutable and have no withdrawal state.
- Joining or leaving courses (ADM-05); this feature only reads membership.
- A cap on attempts per student, deletion or reset of attempts, question reuse rules after answers have been seen, and anti-gaming of repeated attempts (decision 5, open question 5).
- Review of attempts after the student has left the course; attempts on sets that cannot be resolved are not readable.
- Search, filter, sort controls and pagination in the picker; the list is bounded as stated in the plan.
- Per-question topics (a published set has one topic), topic display on the practice page, a recommended-set feature and any AI feature.
- Any change to the URLs, shapes, status codes or error codes of the TEA-03 student routes `GET /api/study/courses/{course_id}/practice-sets` and `GET /api/study/practice-sets/{set_id}`. Only their internals change (they call the provider). They keep TEA-03's 422 for a malformed id (which the practice routes now share) and their own 404 `not_found` code and messages, which differ from the practice routes' 404 `set_not_found`. The picker does not call them. This touches the teacher's TEA-03 files; see "Changes to the teacher's TEA-03 files" in the plan.
- Migrating or deleting old attempts on `intro-se-1`.
- A production seed. The seed is for development databases only.

## Security and AI safeguards
- Server-side only: every practice endpoint and the picker use `current_user(role="student")` through `student_identity.require_student`; the student id comes from the session. Order of checks: 401 `unauthenticated`, 403 `csrf_failed` for unsafe methods, 403 `forbidden`, then (endpoints with a set id in the path) 422 `validation_error` for an id that is not a UUID, then (attempt endpoints) 404 `attempt_not_found` for an unknown or not owned attempt, then 404 `set_not_found` for a set the student cannot access, then state (409, 403 `not_submitted`), then input validation (422). A hidden link is not a control.
- Course access: the provider's single query joins `published_practice_set` to `course_membership` for the session user. It is the one place that decides practice-set access (the same rule as `require_course_member` for lessons: membership row, same 404 for missing and not a member). The companion, progress, the picker and the two TEA-03 student routes call the provider and do not re-implement the check.
- Indistinguishable failures: an unknown valid UUID, a set of another course, and a removed membership share status, `detail.code` and `detail.message` (404 `set_not_found`); no timing-based or field-based hint is added. A malformed id answers 422 before any lookup; that reveals nothing about any record.
- Answer release (SHR-02): the set read response is built only from id, title, question text, null code and choice texts; the answer key (`correct`, `explanation`) lives in the domain object the provider returns but is read only by `practice_logic` (scoring and results after submission) and the companion service (existing rules). Error bodies never contain the key. Results are released only for the student's own submitted attempt on a set the student can still access.
- Published snapshots are immutable and have no application update or delete, so a key cannot change between start and submit; the stored `key_version` stays `v1`. A future feature that edits or withdraws sets must introduce a per-set key version and its own spec.
- Companion and AI: no prompt, model, quota or limit changes. The companion resolves its set through the provider only, so the AI context and the leak check scope cover only sets the student can access; a set the student cannot access gives 404 before any model call and consumes no quota. Pre-submission context excludes keys and explanations exactly as today.
- Untrusted input: the path set id is parsed as a UUID (422 if it is not) before any query (NUL bytes and control characters never reach PostgreSQL, which would reject them); question ids and choice ids in answers are compared exactly; titles, topic names and question texts come from teachers and are rendered as plain text (no HTML interpretation).
- Limits: the picker returns at most the student's member courses and at most 100 sets per course (newest first); the companion loads at most 200 accessible sets (newest first) per message; request bodies keep today's limits. No new rate limit is added to the practice endpoints.
- Concurrent requests (same time): attempt saves and submits keep the STU-04 row lock (`AttemptStore.lock`): two submissions of one attempt give one 200 and one 409 `already_submitted`; saves are merged inside the lock. The set and membership check happens before the lock in its own short read; a membership removal that commits between the check and the write lets that one in-flight request complete (it only touches the student's own attempt), and every request that starts after the removal commits gets 404. A set cannot change in between (immutable snapshots). Different students and different sets never share rows. Simultaneous reads of the picker are independent.
- Normalisation: a set id from the client is parsed with `parse_uuid` (no trimming; the TEA-03 rules) and then used as the lowercase hyphenated string, so alternative spellings of one UUID mean the same set; a value that does not parse is 422. Set ids read from stored attempts are compared exactly as stored, and a stored value that is not a canonical UUID resolves to no set. Attempt ids, question ids (lowercase UUID text from the response) and choice ids (`a` to `d`, lowercase) are compared exactly. Topic and course ids are returned as lowercase hyphenated UUID strings. Titles and names are returned as stored.
- Errors use the shared envelope `{"detail": {"code", "message"}}`; no SQL, paths or exception text. A database failure gives 503 `service_unavailable` and never falls back to fixture data.
- Secrets: none added. The seed reads `DATABASE_URL` and `APP_ENV` from the environment, writes no credentials, and is not run in production.

## Open questions
Each has a recommended answer that the plan uses until a human decides.
1. Picker data source (decision 2 left it open): add one new endpoint `GET /api/practice-sets` (courses, sets, topic and best score in one response, one request per page load) or reuse `GET /api/study/courses` plus `GET /api/study/courses/{id}/practice-sets` per course plus `GET /api/progress`. Recommended: the new endpoint, built on the provider catalog that the TEA-03 routes also use.
