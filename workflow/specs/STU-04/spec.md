# Spec: STU-04 Progress dashboard

Status: Approved by the user on 2026-11-05 (the seven decisions under "Decisions" and the default answers to the open questions were given by the user the same day)

## Goal
From the user stories: a student views lesson completion and saved practice scores so that they can understand how their learning is progressing (US-STU-04-01), and sees the topics that need further practice, identified from their recorded results by a documented rule (US-STU-04-02).

## Behaviour
- A new student page `/student/progress` ("Progress", a new item in the student sidebar between "Practice" and "Inbox") shows three sections, all read from one endpoint, `GET /api/progress`:
  1. Lesson progress: for every course the student is a member of, "N of M lessons complete", plus a list of the five most recently completed lessons. Counts come only from `completion_counts` and `completed_lessons` in `study_lessons/progress.py` (STU-01 contract). The dashboard does not query `lesson_completion` or `published_lesson`.
  2. Practice scores: for every practice set the student has submitted at least once: best score, latest score and the number of submitted attempts. Only submitted attempts count; an attempt in progress is ignored everywhere.
  3. Topics to revise: topics listed by the documented weak-topic rule below, plus an explanation when there is not enough activity.
- Weak-topic rule (documented on the page and here; the numbers are named constants in one module, `progress_rules.py`):
  - For each practice set, only the student's latest submitted attempt counts (repeat attempts replace earlier ones for this purpose).
  - Each answered question belongs to a topic (the question's `topic_id`; a question without a topic, or whose topic row cannot be found, counts under "General").
  - A topic needs practice when the student has answered at least 3 questions on it (`MIN_ANSWERS_FOR_TOPIC = 3`, summed over the latest attempts of all sets) and fewer than 60% of those answers are correct (`WEAK_BELOW_PERCENT = 60`; exactly 60% is not weak). Compared with whole numbers: `correct * 100 < 60 * answered`.
  - A topic with fewer than 3 answers has status "insufficient": the page says there is not enough activity yet and does not call it weak. A topic with at least 3 answers that is not weak has status "on_track".
- Repeat attempts (decision 4): per practice set the page shows the best score (highest correct out of total), the latest score (most recently submitted attempt) and the number of submitted attempts. Scores are "correct / total" counts, not percentages.
- Practice attempts become persistent. A new table `practice_attempt` (Alembic migration) replaces the in-memory `InMemoryAttemptStore` behind the existing `AttemptStore` interface. Existing STU-02 endpoints keep their paths, bodies, error codes and the 404-for-not-owned rule; attempts now survive a server restart and are read in the same way by every server process. Attempts held in memory before the migration are lost (no backfill).
- Practice questions get an optional `topic_id` (a `topic.id` UUID string). The fixture set `intro-se-1` is mapped to topics in code (see plan). The topic name comes from the `topic` table; no topic name is stored in the fixture or in the attempt.
- The student Overview (`/student/overview`) stops showing invented figures. The "Practice average" stat (fake "82%"), the "Time well spent" stat (fake "2.4 hrs"), the "4-day learning streak" and the sample "Your learning rhythm" chart are removed. The Overview shows three real stats from the same `GET /api/progress` call: "Lessons completed", "Practice average" and "Topics to revise", and a link "View full progress" to `/student/progress`.
- "Practice average" on the Overview is the mean, over the practice sets the student has submitted, of the latest score of each set as a percentage, rounded down to a whole number (for example latest 2 of 3 on one set shows "66%").
- Teachers and admins get 403 on `GET /api/progress`. A signed-out request gets 401. The user always comes from the session; no id is read from the request.
- No AI call, no chart, no trend, no time-based figure. The endpoint is read-only and sends scores, counts, titles and topic names only; it never returns an answer key, a correct choice, an explanation, or a question's text or choices.

## Acceptance criteria
Criteria AC1 to AC4 are copied from the user stories (US-STU-04-01 and US-STU-04-02). AC5 onward are derived from them, the user's decisions and the shared acceptance criteria (SHR-01, SHR-02, SHR-04, SHR-05); derived ones are marked.

- [ ] AC1 (US-STU-04-01): The view reflects my saved completion records and attempts.
- [ ] AC2 (US-STU-04-01): No activity produces an explanatory empty state.
- [ ] AC3 (US-STU-04-02): Topics are identified from my recorded results using a documented rule.
- [ ] AC4 (US-STU-04-02): The view explains when there is insufficient activity to identify topics.
- [ ] AC5 (derived, SHR-01): `GET /api/progress` rejects a request without a session (401 `unauthenticated`) and a teacher or admin session (403 `forbidden`). No identity header, query parameter or body field is used: `?user_id=`, `?student_id=`, `X-Student-Id` and `X-Demo-User-Id` are ignored and the response is always the session user's.
- [ ] AC6 (derived, SHR-05): A student never receives another student's counts, scores, attempts or topics, including when the other student shares a course or a practice set. Another student's attempts do not change my scores, attempt counts or weak topics.
- [ ] AC7 (derived, lessons): The lesson section equals the figures of `completion_counts(db, user_id)` and the five newest entries of `completed_lessons(db, user_id)`: only non-withdrawn lessons in member courses count; marking a lesson complete or incomplete (STU-01) changes the next response; the per-course counts add up to `lessons.totals`.
- [ ] AC8 (derived, persistence): Attempts are stored in the `practice_attempt` table. After a new login, a new browser or a new server process, my submitted attempts still give the same scores. The STU-02 endpoints behave as before (same paths, bodies and error codes), including 404 `attempt_not_found` for an attempt that is unknown or belongs to another student.
- [ ] AC9 (derived, repeat attempts): For a set with several submitted attempts the response gives `attempts_submitted` (their number), `best` (the highest correct count) and `latest` (the most recently submitted attempt). An attempt that is in progress is not counted anywhere, and a set with only in-progress attempts does not appear.
- [ ] AC10 (derived, weak topics): With the latest submitted attempt per set, a topic has status `needs_practice` when it has at least 3 answers and `correct * 100 < 60 * answered`; `on_track` when it has at least 3 answers and is not weak; `insufficient` when it has fewer than 3 answers. Boundaries: 3 answers with 1 correct is weak, 3 with 2 correct is on track, 5 with 3 correct (exactly 60%) is on track, 5 with 2 correct is weak, 2 answers with 0 correct is insufficient. A second, newer attempt on a set replaces the older attempt in this calculation.
- [ ] AC11 (derived, rule is stated): The rule's two numbers come from one module (`progress_rules.py`) and are returned in the response as `topics.rule` (`min_answers`, `weak_below_percent`); the page builds its rule text from those values, so the text and the calculation cannot differ.
- [ ] AC12 (derived, no leak, SHR-02): The response contains no `correct_choice`, `explanation`, `key_version`, question text, choice text, or answer map. A student with an in-progress attempt on a set sees nothing of that attempt, and no answer or solution is released by this endpoint.
- [ ] AC13 (derived, empty states): The page shows the exact empty states in "UI states and copy": no courses ("Join a course to start"), courses with lessons but no practice or completion activity, and topics with fewer than 3 answers ("not enough activity yet").
- [ ] AC14 (derived, Overview): The Overview shows only real figures from `GET /api/progress` with the states in "UI states and copy" (loading, signed-out demo, each failure, empty). It no longer shows "82%", "2.4 hrs", the streak, the rhythm chart or any text marked "Sample". The Overview sends one request, `GET /api/progress`, and no longer calls `GET /api/study/courses`.
- [ ] AC15 (derived, UI): The Progress page shows every state in "UI states and copy" with the exact messages and accessible names in the plan's UI contract. No failure shows a raw body, stack trace or HTTP code.
- [ ] AC16 (derived, session): On 401 `unauthenticated` while signed in, the app returns to `/login` (SHR-01 behaviour) and nothing from the earlier session stays on screen; in demo mode the sign-in notice is shown.
- [ ] AC17 (derived, concurrency): Two simultaneous submissions of the same attempt leave one submitted attempt: one request gets 200, the other 409 `already_submitted`, and the attempt is counted once in `attempts_submitted`. Two simultaneous answer saves never produce a 500 or a lost update on different questions. Different students never affect each other.
- [ ] AC18 (derived, migration): One additive Alembic revision after `20261105_tea03_publications` creates `practice_attempt`. Upgrade, downgrade and re-upgrade work on a fresh and on a populated schema; downgrade drops only `practice_attempt`; no existing table or row changes. The dev seed gains one topic row (see plan).
- [ ] AC19 (derived, regression): The existing backend, mocked Playwright, typecheck, lint and format checks pass. Tests that assumed the in-memory store or the Overview sample figures ("Practice average 82%", "Time well spent", weekly chart, streak) or the Overview request to `/api/study/courses` are rewritten against the new behaviour, not deleted.
- [ ] AC20 (derived, docs): `docs/UserGuide.md`, `docs/DeveloperGuide.md`, `docs/SharedDataContract.md` and `workflow/security/test-log.md` describe what works and no more. The UserGuide states the weak-topic rule and the repeat-attempt rule.

Also:
- Refresh: the Progress page and the Overview reload from the server; nothing is kept in browser storage; after a refresh the page shows "Loading your progress…" (Overview: "…" and "Loading…") and then the stored figures.
- Back and Forward: the pages hold no client cache; Back or Forward to the Progress page or the Overview loads it again (one request), so a lesson marked complete or a practice set submitted in between is reflected. Scroll position is not specified.
- After logout or an expired session: protected data is not shown; signed-in users go to `/login`; demo mode shows the sign-in notice (Progress page) or the stat detail "Sign in to see your progress" (Overview). Browser Back after logout shows no progress data (the request is rejected with 401).
- Backend down: the Progress page shows "Could not reach the server. Check your connection and try again." with "Try again" (recovery needs no reload); the Overview stats show "–" and "Could not reach the server."; after the backend returns, reopening the Overview or pressing "Try again" on the Progress page shows the data.
- Longest wait: 10 s per request (`REQUEST_TIMEOUT_MS`). Each of the two screens sends one request, so an error appears at most 10 s after the page opens or after "Try again"; there is no hidden longer wait.
- No generic failure message: every failure uses the exact message in the tables above; there is no catch-all text. "Could not reach the server" appears only for a network failure or timeout (status 0, not a bad response).
- Requests per load and per retry: the Progress page sends exactly one `GET /api/progress` on load and one per "Try again"; the Overview sends exactly one `GET /api/progress` on load and no `GET /api/study/courses`. Development builds run effects twice, so identical in-flight GET requests are shared (never across a session change or a completion save).
- Wrong role: a teacher or admin who opens `/student/progress` or `/student/overview` is redirected by the SHR-01 role guard to their own area (`/teacher/overview`, `/admin/overview`) before any request is sent; the 403 message appears only if the role changes after load; in demo mode (anonymous) the pages request the endpoint, get 401 and show the sign-in notice.
- Link history: push or replace: the sidebar link "Progress", "View full progress", "Open study materials", "Go to practice", every lesson link and "Go to sign in" push a new history entry (nothing replaces); "Try again" does not change the URL. The 401 return to `/login` while signed in is performed by the existing auth hook (SHR-01), unchanged.
- Layout: usable at 390 px and 1440 px width, light and dark theme; the table scrolls horizontally inside its panel at narrow widths; controls keyboard reachable; focus visible; no animation beyond existing styles (reduced motion respected as today); no chart.

## Out of scope
- Charts, trends, streaks, time-on-task, "learning rhythm", weekly or period comparisons, percentage-over-time figures.
- Teacher or admin views of student progress (TEA-05, ADM-01) and any endpoint that takes a user id.
- Editing, deleting or resetting attempts; per-question history; review of past attempts (that stays STU-02: `GET /api/attempts/{id}/results`).
- Practice sets stored in the database, publishing of practice sets and per-question topic assignment by teachers (TEA-04). This feature only adds an optional `topic_id` to the code fixture and a way to read it.
- Course enrolment and joining a course (ADM-05); the empty state only tells the student whom to ask.
- Question reuse after answers have been seen and any cap on the number of attempts per student (open questions below).
- AI features, notifications, export or sharing of progress.
- Offline use.

## Security and AI safeguards
- Server-side only: `GET /api/progress` uses `current_user(role="student")` (through `student_identity.require_student` for the id and a session for lesson helpers); the user id always comes from the session. A hidden button is not a control. Order of checks: 401 `unauthenticated`, 403 `forbidden`, then the work. The route is read-only, so it needs no CSRF token (GET).
- Only the caller's data: lesson counts come from `completion_counts` and `completed_lessons` (member courses only); attempts come only from the store methods filtered by the session student id. There is no parameter that selects another user.
- No answer or solution leakage (SHR-02): the response holds scores (correct and total counts), set ids and titles, course titles, lesson titles and ids, topic ids and names, and per-topic counts. It never holds an answer key, choice ids, selected answers, question ids, question text or explanations. Per-topic counts are computed on the server from the stored list of correctly answered question ids and are only produced for submitted attempts. In-progress attempts are excluded from every query, so the endpoint cannot be used to learn anything about an unsubmitted attempt. Per-topic correct counts after submission reveal no more than the results endpoint, which the student can already read for that attempt.
- Persistence safety: the `practice_attempt` table stores answers and the list of correctly answered question ids with the key version at submission, so later key edits do not rewrite history (US-TEA-04-02). The table is reachable only through `AttemptStore`; the ownership rule (404 for unknown or not owned, identical body) is kept.
- Untrusted input: `GET /api/progress` takes no body and no parameters; any query string is ignored. Titles and topic names come from teachers and are rendered as plain text in the page (no HTML interpretation, no auto-links).
- Limits: the response is bounded: courses by the student's memberships, practice sets by the number of sets in the server (currently one), recently completed lessons at most 5, topics by the topics of those sets. Attempt summaries are produced in the database (grouped per set, one latest row per set), so the number of stored attempts does not change the response size. No AI call, so no model quota; no new rate limit is added for this read-only endpoint (see Open questions about attempt creation).
- Concurrent requests (same time): two submissions of the same attempt are serialised by a row lock (`SELECT ... FOR UPDATE` on the attempt inside `AttemptStore.lock`); exactly one succeeds (200), the other gets 409 `already_submitted`, and the attempt is counted once. Answer saves on one attempt are serialised the same way, so a save never overwrites another save's different questions (answers are merged inside the lock). Two reads of `GET /api/progress` never block each other and return one consistent view of the attempt data (summaries and topics are computed from the same query result); a submission that commits during a read may or may not be included, never half of it. Different students use different rows.
- Normalisation: no user text reaches the endpoint. Student ids come from the session and are compared exactly. Practice set ids and attempt ids are compared exactly as stored (case sensitive, no trimming; an attempt id that does not match gives 404). Topic ids are returned as lowercase hyphenated UUID strings; a question whose `topic_id` is missing or not a known topic row is reported under the topic `{"id": null, "name": "General"}`. Course and lesson ids follow STU-01 (lowercase hyphenated UUID strings).
- Errors use the shared envelope `{"detail": {"code", "message"}}`; no SQL, paths or exception text. A database failure gives 503 `service_unavailable` and never falls back to sample data or to the previous in-memory store.
- No secrets are added; no new configuration variable.

3. "No courses/lessons" (decision 5a): defined here as "no courses" shows "Join a course to start"; a course with no published lessons shows "No lessons published yet." on its line. Confirm the second wording.
4. The Overview "Practice average" (mean of the latest score of each set, rounded down) and the new "Topics to revise" stat replace the removed "Practice average 82%" and "Time well spent" stats. 5. Listed decisions that affect this feature: "Repeat-attempt scoring ... and the rule for identifying weak topics" is answered by the user's decisions 3 and 4 (recorded below). ## Decisions (user, 2026-11-05)
1. Practice attempts are persisted in PostgreSQL (`practice_attempt`, Alembic migration) behind the existing `AttemptStore` interface; locking, concurrency safety and 404 for not owned are kept.
2. Practice questions get an optional `topic_id`; the fixture stays in code and its three questions are mapped to topics (see Open question 1 for the mapping).
3. Weak-topic rule: at least 3 answers on a topic (from the latest attempt per set) and accuracy below 60%; fewer than 3 answers shows an "insufficient activity" explanation; thresholds are named constants in one module.
4. Repeat attempts: per set best score, latest score and number of submitted attempts; weak topics use the latest submitted attempt per set; only submitted attempts count.
5. Empty states: no courses ("Join a course to start"); lessons but no activity; fewer than 3 answers on a topic.
6. Scope: one read-only `GET /api/progress` (student only, user from the session) and one Progress page; no charts or trends.
7. The Overview's fake "82%" and sample week chart are replaced by real figures from the same endpoint; Overview states are specified.
