## Data model
No schema change, no migration, no new table, column, index or stored value. Reads and writes are those of the existing ADM-02, ADM-03 and ADM-04 tables. The follow-up count reads `feedback_responses` (`id`, `user_id`), `user` (`id`, `role`, `access_status`, `archived_at`) and `admin_messages` (`kind`, `source_feedback_response_id`); the existing foreign-key index paths are enough for the expected volume (no index added; if the count is slow at scale, report it instead of adding one). The hub keeps no state outside React memory; nothing goes to local or session storage.

### The chooser request (not a new endpoint)
`GET /api/admin/feedback/forms?limit=100&offset=0` on entering `/responses`. Same endpoint, response `{items: FormSummary[], next_offset: integer|null}` as ADM-02 (`limit` 1 to 100, default 20). `FormSummary` fields used: `id`, `title`, `state` (`draft`|`open`|`closed`), `response_count`. Browser-side rule: drop `state === "draft"`; sort order is the server's. If `next_offset !== null` show the truncation note. Error mapping is the ADM-02 dictionary (E01, E02, E04, E05, E06, E07, E08; E03 and V codes cannot occur on a list).

### The new endpoint: follow-up count (Decision Q15)
`GET /api/admin/messaging/followup-counts`, in `messaging.py` on the existing `router` (class `MessagingRoute`, so unexpected failures map to `MESSAGING_ERROR` and database failures to `MESSAGING_UNAVAILABLE`). Name confirmed against the router: messaging routes are `/api/admin/messaging/...` and the count is ADM-04 reply state; a `/api/admin/feedback/...` path would need a second error shape and a second quota scheme.
- Access: dependency `Depends(admin)` (the existing function in `messaging.py`: `store.begin(db, request, "admin")` then `store.quota(actor, "read")` for GET), so 401 anonymous and 403 student and teacher come from the shared `current_user(role="admin")` before any data access, with the existing auth error shape.
- Request: no body, no path or query parameters. `valid.query(request)` with no allowed keys rejects any query string with 422 `INVALID_REQUEST` (existing message).
- Response 200: `{"unanswered_responses": <integer >= 0>}`, exactly that one key. Header `Cache-Control: no-store` (set by the existing middleware, as for the sibling routes; the test asserts it). No user id, name, email, form id, response id, title or text.
- Errors (existing dictionary, shape `{"detail": {"code", "message", ...}}`): 401 and 403 (shared auth), 422 `INVALID_REQUEST`, 429 `MESSAGING_RATE_LIMITED` with `detail.retry_after_seconds` > 0 (20 reads per minute per admin, the shared `read` bucket), 500 `MESSAGING_ERROR`, 503 `MESSAGING_UNAVAILABLE`. All carry `no-store`. The hub treats every non-401 error silently.
- Function: `messaging_store.unanswered_response_count(db) -> int` (name proposed, developer confirms): one `SELECT count(*)` over `FeedbackResponse` joined to `User` on `FeedbackResponse.user_id == User.id` where `User.role IN ('student','teacher')`, `User.access_status == 'enabled'`, `User.archived_at IS NULL` (the same conditions as `response_recipient`; reuse a shared predicate helper rather than copying the three conditions) and `NOT EXISTS (SELECT 1 FROM admin_messages m WHERE m.kind = 'feedback_response' AND m.source_feedback_response_id = FeedbackResponse.id)`. The route returns `committed(db, {"unanswered_responses": n})` like its siblings. Read-only: no insert, update, delete, no lock beyond `begin`'s shared account-change lock, no log of values.
- Why this definition: responses are always identified (the table's `user_id` is required and tied to a recipient row, so no anonymous responses exist); a reply is the only ADM-04 artefact tied to a response (`AdminMessage.source_feedback_response_id`), so "no reply message exists" is derivable without new data; respondents who cannot be replied to (disabled or archived) are left out because `RECIPIENT_UNAVAILABLE` would reject the reply anyway.
- Cross-user: global value, equal for every admin; no per-admin state. Concurrency: single statement, snapshot per statement; a reply committed during the read is either counted or not, never half. Deleted responses are not rows, so not counted.

### The two count requests on existing endpoints (Decision Q11)
Sent once per hub mount by `HubCountsProvider` (below), in parallel with the follow-up count, `GET` only, `timeoutMs: 15000`, `cache: "no-store"`, aborted on unmount and logout, no retry on failure:
1. `GET /api/admin/feedback/forms?limit=100&offset=0` returns `{items: FormSummary[], next_offset}`. Forms count = items with `state === "open"`; draft count = `state === "draft"`; Responses count = sum of `response_count` over `state !== "draft"`; `truncated = next_offset !== null`.
2. `GET /api/admin/feedback/analyses?limit=50&offset=0` returns `{items, next_offset}` (ADM-03, `limit` maximum 50). Analysis count = `items.length`; `truncated = next_offset !== null`.
3. `GET /api/admin/messaging/followup-counts` returns `{unanswered_responses}`; Follow-up count = that number (never truncated; display `99+` when above 99, description carries the true number). Same options as above.
Only a 401 is surfaced (shared session-end flow); every other failure (including 429) leaves a never-loaded count `unavailable` silently, or keeps the last good value on a refetch. Errors in one request never affect the others, the tabs or the screen. Totals in a hub load: `/forms` 4 GETs (list + 3), `/responses` 4, `/analysis` 5, `/analysis?form=` 5 + the picker's own, others 3 + the screen's own.

### Event-driven refetch (Decision Q13)
Mounted-hub flow: `HubCountsProvider` loads the three sources once, then calls `subscribeHubCountChange` and refetches only the source named by an emitted topic: `forms-changed` -> request 1 (updates both the Forms and Responses counts); `analyses-changed` -> request 2; `followup-changed` -> request 3. Same options (15 s, no-store, no retry). Per source keep one `AbortController`; a new refetch aborts the older one of that source (latest wins, aborted responses ignored). A refetch result replaces the stored count only when it succeeds; failure keeps the previous `ready` value (or stays `unavailable` if none); 401 ends the session. Unsubscribe and abort all on unmount and logout. Emitters (success only, in the service functions, so old pages and new hub share them): `feedbackApi.ts` create form, publish, close and delete response (emits `forms-changed` and `followup-changed`); `feedbackAnalysisApi.ts` generate (create) analysis -> `analyses-changed`, delete analysis -> `analyses-changed`; the messaging API service send-preview call -> `followup-changed` only when the sent preview's kind is `feedback_response`. Delete (response or analysis) also emits on a 404 answer. No emit on save draft, announcement send, previews, reads, any failure, timeout or abort. Function names of these services are not confirmed in this plan: the developer maps each row of the spec's notification table to its function and reports differences in `workflow/notes.md`.

Per-screen labelled entries (hub-level; inner screens inherit the old plans' entries unchanged):

Retry of a failed load: 1 request (the screen's own; counts are not re-requested). The chooser: 1 on entry, 1 per Retry, 0 on selection. "Analyse this form": 0 of its own; the Analysis screen then sends its 2 landing requests plus the picker's own request(s) once for the preselected form. - No generic failure message: every failure uses its exact message from the spec; the chooser's messages come from the ADM-02 dictionary; the network message only for a fetch rejection that is neither an abort nor the 15-second timeout.
- Refresh: exactly as in `spec.md` (URL restores tab and screen; that URL's requests only).
- Back and Forward: exactly as in `spec.md` (remount and reload, no resent mutation).
- Expired session or logout: exactly as in `spec.md` (401 ends the session, data and polling cleared, no storage).
- Backend down: exactly as in `spec.md` (shell always renders, counts silently absent, each screen shows its own message and Retry).
- Longest wait before an error: 15 seconds per request, then the screen's own timeout message, as in `spec.md`; the analysis AI step is bounded at 780 seconds on the server and is progress, not an error wait.

## Decisions
- Hub base `/admin/feedback-hub` with path-based tabs (Q1, closed); old routes untouched until phase 5, then redirected (AC21).
- Inner screens are shared components, not copies (Q2, closed); the old pages are thin wrappers until phase 5.
- Backend change limited to the dev seed (Q3, included) and one read-only endpoint, `GET /api/admin/messaging/followup-counts` (Q15); the chooser and the other counts reuse `GET /api/admin/feedback/forms` (`limit=100`) and `GET /api/admin/feedback/analyses` (`limit=50`); the frozen set is now 30 routes.
- Counts are event-driven in the browser (Q13): load once per hub mount, refetch only the affected source after a successful count-changing mutation via `lib/hubCountEvents.ts`; failed refetch keeps the old value; no refetch on tab clicks, no polling, no push; other admins' changes appear after remount. Analysis `50+` cap (Q14), duplicate forms request (Q16) and loss of demo "Feedback insights" (Q17) accepted.
- Responses landing is the new chooser (Q4). No hub heading (Q8); label "Feedback hub" (Q9).
- Tab counts (Q11): Forms, Responses, Analysis only, loaded once per hub mount from the two list endpoints, silent on failure, described through `aria-describedby` so tab names stay exact; no Follow-up count (no source). The hub makes no polling or refresh request.
- Shortcut "Analyse this form" (Q6) is a hub-only link to `/analysis?form={id}`; the Analysis selection preselects through the picker's own handler.
- Phase 5 removes all three admin nav items including the demo "Feedback insights" with its page, route, sample data and only-covering tests (Q5, after coverage mapping); `pr.md` and `retro.md` of old specs are archived under `docs/archive/<id>/` (Q10); respondent-side criteria live in `retained-criteria.md` (Q7); the test-designer may read the old ADM-02/03/04 specs (Q12).
- Tabs are navigation: each tab is a URL, push on activation, remount on switch, nothing cached (so request counts equal the old screens and private data is never reused across tabs).
- Orchestration is lighter, as decided in the migration plan (decision 3): tests first by the test-designer, build by the developer, one verifier pass for phase 3 and one for phase 5; the cross-user and concurrency tasks of the template are omitted because the feature adds no stored records or endpoints.
- The three remaining open questions in `spec.md` (meaning of "needs attention", shared read quota, badge wording) use the defaults stated there until the human decides.
- Phase 5 keeps the count endpoint, its tests, `lib/hubCountEvents.ts`, `HubCountsProvider` and the emit calls (AC30).
