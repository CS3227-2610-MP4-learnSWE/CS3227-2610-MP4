# Spec: ADM-08 Feedback hub

Status: Approved by the human on 2026-11-12 (Gate B; was: Draft Phase 1, revised 2026-11-12 with the human's answers to Open questions 1 to 12 and then to the five follow-on questions, all closed in "Decisions on the former open questions"; approved with the stated defaults). One new small read-only backend endpoint is added by this revision (Follow-up badge, AC28). Supersedes ADM-02, ADM-03 and ADM-04 only after approval and the deferred cleanup phase (phase 5 of this feature, see `tasks.md`); until then the old features keep working unchanged (see `workflow/plans/CONSOL-01-migration-plan.md`, phase 3).

## Goal
An admin opens one area, the "Feedback hub", with four tabs: Forms, Responses, Analysis and Follow-up, and runs the whole feedback loop there: prepare, publish and close targeted forms (ADM-02), review collected responses (ADM-02-04, plus the response delete added to ADM-03), analyse selected responses with statistics and an AI summary and open the cited evidence (ADM-03), and send one-to-one replies and announcements (ADM-04). The hub is a lighter shell: it changes where each screen lives and how screens link to each other, not what any screen or endpoint does. Data is real only (forms, responses, analyses and messages that exist); nothing is mocked or sampled. Stories: US-ADM-08-01 to US-ADM-08-08.

## Behaviour

### What changes and what does not
- **Changes:** one new admin route family `/admin/feedback-hub/...` (route table below), a tab bar around the existing screens, links between screens that stay inside the hub, one new small screen (the form chooser on the Responses tab), three small additions (tab counts kept up to date by in-browser events, the "Analyse this form" shortcut and the Analysis selection reading one query value `form`), one admin navigation link "Feedback hub", and one new read-only backend count endpoint for the Follow-up badge.
- **Does not change:** every existing backend endpoint, schema, error code, limit and quota (ADM-02, ADM-03, ADM-04 as built; the only backend addition is the count endpoint in "Tab counts"); the student and teacher survey forms and inboxes (`/student/inbox`, `/teacher/inbox`, `/student/feedback/{form_id}`, `/teacher/feedback/{form_id}`) and the unread badge; the text, states and request counts of each inner screen. The inner screens are the same components as the old pages, made independent of their address (plan, "Components and modules").
- **Old routes until phase 5:** `/admin/feedback`, `/admin/feedback/new`, `/admin/feedback/{form_id}`, `.../edit`, `.../responses`, `.../responses/{response_id}`, `.../responses/{response_id}/reply`, `/admin/feedback/analysis...`, `/admin/announcements` and `/admin/announcements/new` keep working exactly as today, and their nav links ("Feedback forms", "Announcements") and the demo item "Feedback insights" stay. In phase 5 all three nav items are removed (AC25). Links rendered inside the hub never point to an old route. In phase 5 the old routes are redirected to the hub (AC21) and the old pages, specs and tests that only covered them are removed.

### Page and tabs
- One page area at `/admin/feedback-hub`. The hub adds no heading of its own: it shows the label "Feedback hub" and one muted line "Create forms, review responses, analyse feedback and follow up with respondents, all in one place." as plain text, then the tab bar, then the selected tab's screen. Each inner screen keeps its own heading level 1 exactly as in the old specs (so the old assertions port unchanged).
- Tab bar: a tablist named "Feedback sections" with four tabs in this order: "Forms", "Responses", "Analysis", "Follow-up". The selected tab follows the URL. Activating a tab (click, Enter or Space) navigates to that tab's landing URL (history push). Left and Right arrow keys move focus between tabs (Home and End to the first and last) without activating; Tab moves into the panel. Switching tabs unmounts the current screen and mounts the destination screen, which loads fresh; nothing is cached between tabs. In-flight requests of the screen being left are aborted and their late responses ignored (existing behaviour of the inner screens).
- The tab bar stays visible on every hub URL, including detail, editor, result and review screens; the selected tab is the one that owns the URL.

### Tab counts
All four tabs can show a small count badge, built from two existing list endpoints and one new read-only endpoint (30 frozen routes, see AC1):
| Tab | Badge number | Source | Visible badge | Description read by screen readers (`aria-describedby`) |
|---|---|---|---|---|
| Forms | Forms in state `open` | `GET /api/admin/feedback/forms?limit=100&offset=0` (count `state === "open"`) | `{open}` | `{open} open forms` (singular `1 open form`); when drafts exist, `, {draft} drafts` (`, 1 draft`) is appended |
| Responses | Sum of `response_count` over forms not in state `draft` | same response as above | `{sum}` | `{sum} submitted responses` (`1 submitted response`) |
| Analysis | Saved analyses | `GET /api/admin/feedback/analyses?limit=50&offset=0` (count of `items`) | `{n}` | `{n} saved analyses` (`1 saved analysis`) |
| Follow-up | Feedback responses still without a sent reply (definition below) | NEW `GET /api/admin/messaging/followup-counts` (admin only, read-only, body `{"unanswered_responses": n}`) | `{n}` (a number above 99 is shown as `99+`; the description always carries the true number) | `{n} responses without a reply` (`1 response without a reply`) |
- **Follow-up count definition.** "Needs attention" means a submitted feedback response (any form state, draft forms cannot have responses) that has no sent reply yet and whose respondent can still be replied to. Precisely, the server counts rows of `feedback_responses` where (a) the respondent account has role student or teacher, is enabled and not archived (the same test `response_recipient` applies when a reply preview is created, so every counted item can actually be answered) and (b) no `admin_messages` row exists with `kind = 'feedback_response'` and `source_feedback_response_id` equal to the response id. A reply sent by any admin counts as answering it (messages are shared by all admins, ADM-04). Announcements never answer a response. All feedback responses in this product are identified (every response row belongs to a recipient account, ADM-02), so nothing anonymous exists to exclude; if anonymous responses are ever added they must be excluded from this count. There is no "dismiss" or "mark as handled": the count falls only when a reply is sent or the response is deleted.
- **When counts load (event-driven, Decision Q13).** The three requests (forms list, analyses list, follow-up count) are sent once each when the hub mounts (entering any hub URL, refresh, Back from outside the hub), in parallel with the screen's own landing requests. After that a count is refetched only when an inner screen reports, through the in-browser notification described below, that a mutation changed it; and then only the affected source is requested. There is no refetch on tab clicks or tab switches, no server push, no polling and no timer. Changes made by other admins, and responses submitted by students and teachers, are not reflected until the hub is mounted again (accepted).
- If a list reports `next_offset` not null the badge shows `{n}+` and the description says `at least {n} ...` (only the newest 100 forms, or 50 analyses, are counted; Decision Q14 accepts `50+` for analyses). A count of 0 shows no badge and no description. While the first load is pending, and when a count request fails for any reason (401 excepted), nothing is shown for a count that never loaded: no spinner, no placeholder, no message, no Retry, and the tab stays fully usable. A failed refetch keeps the previously shown value (Decision Q13: stale beats blank, because a count of the last known real data is better than a flicker; no message and no Retry either). A 401 ends the session as everywhere else (AC11).
- The tab's own accessible name stays exactly "Forms", "Responses", "Analysis", "Follow-up" (the badge element is `aria-hidden="true"`; the count is delivered through `aria-describedby` pointing at a visually hidden description element).
- Counts are real data of the signed-in admin's own view (same permissions as the screens); they are rendered as text only.

#### In-browser count notifications (shared module `lib/hubCountEvents.ts`)
A tiny module-level event bus with no payload and no storage. Exports `type HubCountTopic = "forms-changed" | "analyses-changed" | "followup-changed"`, `emitHubCountChange(topic: HubCountTopic): void` and `subscribeHubCountChange(listener: (topic: HubCountTopic) => void): () => void` (returns the unsubscribe function). Emitting with no subscriber (every old page, or any screen outside a mounted hub) does nothing, so the old routes behave exactly as before. Only the hub's count provider subscribes, on mount, and unsubscribes (and aborts its in-flight count requests) on unmount and logout. The mutation functions of the shared API services emit after the server confirmed success (2xx), never before and never on a failure or an uncertain outcome (timeout, network error):
| Mutation (success) | Topic(s) emitted | Requests the hub then sends |
|---|---|---|
| Create form (POST forms) | `forms-changed` | 1 GET forms list (`limit=100&offset=0`), updates the Forms and Responses badges |
| Publish form | `forms-changed` | 1 GET forms list |
| Close collection | `forms-changed` | 1 GET forms list |
| Save draft (PUT form) | none (no count changes) | 0 |
| Delete a response (DELETE; also when the server answers 404 because it is already gone) | `forms-changed` and `followup-changed` | 1 GET forms list and 1 GET follow-up count (2 in total) |
| Generate analysis (POST analyses, including an idempotent replay answered 200) | `analyses-changed` | 1 GET analyses list (`limit=50&offset=0`) |
| Delete an analysis (also when the server answers 404 because it is already gone) | `analyses-changed` | 1 GET analyses list |
| Send a reply to a feedback response (send preview of kind `feedback_response`) | `followup-changed` | 1 GET follow-up count |
| Send an announcement | none (announcements change no count) | 0 |
| Create preview, search, page, recipient reads, everything else | none | 0 |
Rules: one emit leads to exactly one request of the affected source, sent immediately (no debounce). If a refetch of the same source is still in flight when another emit arrives, the older request is aborted and ignored and one new request is sent (latest wins); the other sources are untouched. The two forms-derived badges (Forms, Responses) are always updated from the same single forms request. A refetch never shows a spinner, message or Retry. Opening a receipt or preview with `?review=` for a message that was already sent emits nothing (it is a read). A mutation whose outcome is unknown does not emit; the badge corrects itself at the next hub mount.

### Cross-tab shortcut: "Analyse this form"
On the Responses tab's "Submitted responses" list (`/responses/{form_id}`), a link "Analyse this form" is shown next to "Choose another form". It pushes `/analysis?form={form_id}`. The Analysis selection screen (`/analysis`) reads the single query value `form`: once its forms list has loaded, if `form` equals (case-insensitively, canonical UUID) the id of a form offered for analysis, that form is preselected exactly as if the admin had chosen it in the form picker (the same follow-up requests the picker makes, once); otherwise nothing is preselected and the status "The linked form is not available for analysis. Choose a form below." is shown. Nothing is generated or ticked automatically; the admin still selects responses and chooses "Generate analysis". The query is left in the address; choosing another form in the picker does not change the address; the Analysis tab click goes to `/analysis` without the query.

- Review state of both composers stays in the query `?review={preview_id}` exactly as in ADM-04, on the hub URLs above.
- A first segment that is not one of `forms`, `responses`, `analysis`, `follow-up` is replaced with `/forms`. A known first segment followed by a path that matches no row (for example `/forms/{form_id}/edit/extra`) shows the screen "This Feedback hub page does not exist." (UI table) inside the hub with the tab bar. Identifiers are not validated by the hub: a well-formed path with an unknown or malformed id loads the inner screen, which shows its own not-found message from its own server response (ADM-02 E03, ADM-03 `analysis_not_found` and `evidence_not_found`).
- Everything after the first path segment, and the query, is owned by the inner screen; the hub shell reads nothing from the query. The only new query value is `form` on the Analysis selection screen (read by that screen, not by the shell).

### Responses tab landing (new)
The Responses tab needs a landing because the old review flow started from a form's detail page. The landing is a form chooser: one `GET /api/admin/feedback/forms?limit=100&offset=0` (the ADM-02 list endpoint, `limit` maximum 100); forms in state `draft` are left out in the browser (a draft cannot have responses); the rest are shown as options of one native select. Choosing a form navigates (push) to `/responses/{form_id}` and sends no request itself. If the list reports more forms (`next_offset` not null) a note says only the first 100 are listed (UI table). The same screens as before follow: the list "Submitted responses" and the response detail with its delete and reply actions.

### Follow-up tab
The tab landing is the announcement composer (the only ADM-04 screen that does not start from a response). Replying to one respondent starts from a response detail ("Respond to feedback") and opens the reply composer under this tab. There is no sent-message history screen (out of scope, as in ADM-04).

After the first load, a count-changing mutation adds only the refetches in "In-browser count notifications" (one GET per affected source: 1 for create, publish, close, generate, analysis delete and reply send; 2 for a response delete), and nothing else. Entering a URL then sends, besides those, exactly: `/forms` 1 GET forms list (same query as the old list); `/forms/new` 1 GET associations; `/forms/{form_id}` 1 GET form; `/forms/{form_id}/edit` 1 GET form and 1 GET associations; `/responses` 1 GET `/api/admin/feedback/forms?limit=100&offset=0`; `/responses/{form_id}` 1 GET responses (same query as the old list); `/responses/{form_id}/{response_id}` 1 GET response detail; `/analysis` 1 GET forms and 1 GET analyses (limit 20), and with `?form={form_id}` additionally, once and after the forms list, exactly the requests the form picker's own choice sends; `/analysis/{analysis_id}` 1 GET analysis, then one GET every 2 seconds only while the AI step runs (ADM-03 polling rules); `/analysis/{analysis_id}/responses/{label}` 1 GET evidence and 1 GET analysis (optional context, as ADM-03); `/follow-up` 1 GET recipients (`role=student`, empty search, page 1, page size 50); `/follow-up?review={preview_id}` 1 GET preview; `/follow-up/reply/{form_id}/{response_id}` 1 GET recipient; the same with `?review=` 1 GET preview. Retry of a failed load: exactly 1 request (that load's). Choosing a form in the chooser, "Choose another form", "Analyse this form", activating a tab: 0 requests of their own. All other screen actions send what the old specs say (one request per save, publish, close, submit, search, page, preview, send, generate, delete). Development builds send no duplicates. In-flight requests are aborted on unmount, tab switch and logout; late responses are ignored.

- Refresh: A browser refresh on any hub URL restores the tab and screen from the URL and sends that URL's requests (table above) and nothing else; the inner screens reset exactly as before (editor unsaved changes lost with the existing native warning, analysis selection and ticks reset, a running AI step resumes polling, a composer without `review` is empty, a composer with `review` reloads the durable preview or receipt with one GET and never sends).

## Security and AI safeguards
- Access: only active admins use the hub. The server is the control: every endpoint used (frozen list in `plan.md`) keeps its existing admin or recipient dependency and its 401, 403 and uniform 404 behaviour; the hub's redirect for other roles is a convenience, not the control. The hub adds exactly one endpoint, `GET /api/admin/messaging/followup-counts` (admin only on the server, read-only, `no-store`, rate limited in the messaging `read` bucket, body only a number, no user id or response text), and sends no user id, course id or record id the old screens did not already send; the other two count requests are the same list endpoints with fixed query values (`limit`, `offset`) and are admin-only on the server like the screens' own calls. The count is global (the same for every admin) and reveals only how many responses lack a reply, not whose they are; the in-browser notification bus carries no data and is never persisted. The `form` query value of the shortcut is never sent to the server as such: the Analysis screen compares it with the ids returned by the admin's own forms list and uses only a matching id, so a forged value can only produce the "not available" status. Hidden, malformed and foreign ids keep the old uniform not-found responses.
- Private data: raw feedback and respondent identity stay admin-only (SHR-05). The hub shows the same data as the old pages and adds none: the chooser reads form titles, state and counts from the existing list. Nothing is written to local or session storage; no response text, answers, names or message bodies are logged or sent to analytics.
- AI: the hub adds no AI call and no prompt. ADM-03 analysis keeps every safeguard (SoC LLM only via the shared client, free-text answers as untrusted data, no identity or choice and scale answers sent, strict JSON validation, evidence labels checked, plain-text rendering, 500-response cap, one running AI step per admin, caller limits, usage label `ADM-03`). Rendering stays plain text: no inner component changes how respondent or model text is rendered.
- Limits (SHR-03): all existing limits stay (ADM-02 quotas and body caps, ADM-03 500 responses and AI limits, ADM-04 500 recipients and quotas). The chooser reads at most 100 forms in one request.
- Concurrent requests (same time): the hub adds no write path, so no new write race exists. The count endpoint is one read-only SQL statement: while a reply is being sent the value is either before or after it (never negative, never a partial state), at most one send behind; two admins reading at once get the same value; the per-admin rate limit applies per account; repeated refetches after quick successive mutations replace each other in the browser (latest wins); the existing guarantees stay and keep their tests (ADM-02 version checks, one publication, idempotent close and submit; ADM-03 one 201 and one 409 for simultaneous analyses, idempotent `request_id`, delete versus job writes; ADM-04 idempotent send per preview). Two quick tab switches leave only the last destination mounted; aborted requests of the earlier screen never update the new screen; the form editor's dirty guard prevents leaving mid-save silently.
- Normalisation: the hub trims nothing and parses no ids: route params are passed unchanged to the inner screens, which keep their own normalisation (ADM-02 canonical UUIDs and 404 for malformed ids, ADM-03 lowercased UUIDs and uppercased evidence labels, ADM-04 trimmed and bounded text). The tab is chosen by an exact, case-sensitive match of the first path segment (`forms`, `responses`, `analysis`, `follow-up`); any other value is replaced with `/forms`. Query values are not read by the hub; `review` is read only by the Follow-up screens.
- Decisions from "Decisions to resolve before implementation" that affect this feature: (a) identified versus anonymous feedback, retention and deletion: ADM-02 approved identified responses visible to admins, ADM-03 added admin deletion of responses and indefinite retention of analyses; the project-level retention and deletion rule is still open and the hub changes none of it; (b) exact SoC LLM quotas, model configuration and resource measurements: still open (see ADM-07 Open question 18 for the dated observations); ADM-03's placeholders (20 per minute, 300 per day, 15 s) are unchanged and the hub shows no quota as fact.
