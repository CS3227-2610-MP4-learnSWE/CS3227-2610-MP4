Downgrade drops `auth_session`, `ux_user_email`, the CHECK, and the two `user` columns. Existing user rows and ids are untouched. New signup user ids are `u-` + 32 lowercase hex characters (fits varchar(64); distinct from `demo-*`).

Password hash format: `scrypt$<n>$<r>$<p>$<salt_b64>$<hash_b64>` with n=16384, r=8, p=1, 16-byte random salt, 32-byte derived key (`hashlib.scrypt`, `maxmem=64 MiB`). Verify parses the parameters from the stored string, recomputes and compares with `hmac.compare_digest`. A module-level dummy hash is verified when the email is unknown or has no hash.

Session token: `secrets.token_urlsafe(32)`; cookie value is the raw token; database stores `sha256(token).hexdigest()`.

Roles remain `student`, `teacher`, `admin` (existing CHECK). Role is never written from request data; signup code path hard-codes `"student"`.

## API endpoints

All JSON. Errors use the existing envelope `{"detail":{"code","message", ...extra}}` through `errors.ApiError`. Every `/api/auth/*` response has `Cache-Control: no-store`. Request bodies are parsed in the handler with Pydantic models using `extra="forbid"` and strict types; a validation failure is converted to 422 `validation_error` with `fields` (list of offending field names, never echoing values). This keeps the 422 shape of other routes unchanged (no global validation handler change).

`User` object: `{"id": str, "email": str | null, "display_name": str, "role": "student"|"teacher"|"admin"}`.

| Method and path | Auth | Request | Success |
|---|---|---|---|
| `POST /api/auth/signup` | none | `{"display_name": str, "email": str, "password": str}` exactly these three | 202 `{"status":"accepted"}`; no cookie |
| `POST /api/auth/login` | none | `{"email": str, "password": str}` exactly these two | 200 `{"user": User, "csrf_token": str}` and `Set-Cookie` |
| `POST /api/auth/logout` | session optional | none (empty body) | 200 `{"status":"ok"}`; clears cookie (`Max-Age=0`, same flags) |
| `GET /api/auth/me` | any session | none | 200 `{"user": User, "csrf_token": str}` |
| `GET /api/courses/{course_id}` | any role, member | none | 200 `{"id": uuid, "title": str, "created_at": iso-Z}` |

Cookie header on login: `learnswe_session=<token>; HttpOnly; Path=/; Max-Age=<ttl>; SameSite=<value>[; Secure]`.

Login/signup input limits and normalisation: `email` trimmed then lower-cased, 1 to 254 chars; `password` 1 to 1024 chars on login (not stripped; longer is 422), 10 to 128 on signup; `display_name` trimmed 1 to 100 code points. Login does not apply password rules (a rule change must not lock out old accounts), only the size cap.

Logout behaviour: if a valid session cookie exists, require matching `X-CSRF-Token` (else 403 `csrf_failed`), delete the row, clear the cookie. If no or an invalid cookie, still 200 and clear the cookie. Origin check applies in both cases.

Order of checks in `/api/auth/login`: config validate (503) then Origin (403) then body parse (422) then rate limit (429) then credential check (401) then create session. Signup: config (503), Origin (403), body parse (422), rate limit (429), then create-or-ignore. (Parse before limit is deliberate; invalid requests still count toward the signup IP limit.)

Rate limit accounting: login failures (401 results) are recorded against `login:email:<normalised email>` and `login:ip:<ip>`; the limit check happens before verification and returns 429 if either key is at its limit. Every signup request that passes parsing is recorded against `signup:ip:<ip>`. 429 body: `{"detail":{"code":"rate_limited","message":"Too many attempts. Try again later.","retry_after_seconds":N}}` plus `Retry-After: N` (matches the existing `error_response` handling of `retry_after_seconds`).

### Error codes

| Status | `detail.code` | Condition |
|---|---|---|
| 401 | `unauthenticated` | no/unknown/expired session cookie, or user row deleted |
| 401 | `invalid_credentials` | login failed for any reason (wrong password, unknown email, no hash) |
| 403 | `forbidden` | authenticated but role not permitted |
| 403 | `csrf_failed` | state-changing request with missing/wrong `X-CSRF-Token`, or disallowed `Origin` |
| 404 | `not_found` | course missing or user not a member |
| 422 | `validation_error` | body or path invalid; `fields` lists names |
| 429 | `rate_limited` | limits above; includes `retry_after_seconds` |
| 503 | `service_unavailable` | database or auth configuration unavailable/invalid |

The student routes' former 401 `missing_student` becomes 401 `unauthenticated`. Their other codes (`attempt_not_found`, `set_not_found`, `already_submitted`, `incomplete`, `rate_limited` etc.) are unchanged.

### Shared `current_user` contract (documented for teammates in `docs/DeveloperGuide.md`)

```python
# auth/dependencies.py
@dataclass(frozen=True)
class AuthUser:
    id: str
    email: str | None
    display_name: str
    role: str                      # "student" | "teacher" | "admin"

def current_user(role: str | Iterable[str] | None = None) -> Callable[..., AuthUser]:
    """Dependency factory. Use as Depends(current_user()) or Depends(current_user(role="teacher")),
    or role=("teacher", "admin"). Order: 401 unauthenticated, 403 csrf_failed (unsafe methods),
    403 forbidden. Never reads any identity header."""

def require_course_member(db: Session, user: AuthUser, course_id: UUID) -> Course:
    """404 not_found unless a course_membership row exists for (course_id, user.id).
    Same response for a missing course and a non-member."""
```

Usage example for a route: `def handler(course_id: UUID, user: AuthUser = Depends(current_user(role="teacher")), db: Session = Depends(get_session)): course = require_course_member(db, user, course_id)`. For a teacher route, role is checked by `current_user` and the membership by `require_course_member`; both must pass. Admin routes use `current_user(role="admin")` and must not assume course membership. Record-level checks (for example "attempt belongs to user") stay in the feature that owns the record, and must return the same 404 for missing and not-owned.

Per-request sequence in `current_user`: read cookie by `SESSION_COOKIE_NAME` -> `sha256` -> `load_session` (joins user, checks `expires_at > now`) -> unsafe method: `check_origin` and compare `X-CSRF-Token` with `compare_digest` -> role check. DB session comes from `get_session`; the user is re-read each request, so deletion or role change is immediate.

### Seed script

`uv run python -m auth.seed` (from `src/backend`, after `alembic upgrade head` and `python -m teacher_materials.seed`). Fixed targets: `demo-student` (role student), `demo-teacher` (role teacher), `demo-admin` (role admin, created if missing with display name "Admin"; no memberships). For each role whose `SEED_<ROLE>_EMAIL` and `SEED_<ROLE>_PASSWORD` are both set: normalise email, check password rules, then set `email` and `password_hash` only if the user's `password_hash` is NULL (or `--reset-passwords` is given). Prints one line per role (`seeded`, `unchanged`, `skipped: <reason>`), never the password. Exit code 0 normally; non-zero if an existing user has a different role than expected or the email is already used by another user. Idempotent.

## Decisions

- Reuse the existing `user` table (additive columns) instead of a parallel `users` table, so memberships, materials and drafts keep working (approved).
- Admin gets no implicit course access; `require_course_member` has no admin bypass (approved).
- Stdlib scrypt over a new dependency (approved). No new Python or npm dependencies.
- 12-hour absolute session, no idle timeout (approved).
- Demo access is kept: the guard treats anonymous as demo mode while `VITE_ENABLE_DEMO_ACCESS` is not `false`; real-session routes ignore demo identity entirely, so demo mode is a presentation concern with no server privilege.
- Signup is non-enumerating by returning 202 without logging in, then the user signs in; chosen over "409 email taken" because there is no email verification channel.
- Session lookup is by hashed token in PostgreSQL (not a signed cookie), which allows immediate revocation and role re-evaluation.
- CSRF: per-session token header plus Origin check; SameSite is defence in depth, not the only control.
- Per-process in-memory rate limiting reusing the existing sliding-window class; adequate for one instance, documented limitation for several.
- Sync route handlers (threadpool) so password hashing does not block the event loop.
- Student routes keep `require_student(...) -> str` so downstream code is untouched; `AuthUser` is returned by `current_user`.
- `GET /api/courses/{course_id}` is included as the minimal, real, testable use of `require_course_member`.
