# Spec: ADM-07 Analytics hub

Status: Draft (Phase 1, awaiting Gate B review). Supersedes ADM-01 and ADM-06 only after approval and the phase 5 deletion gate; until then the old features keep working unchanged (see `workflow/plans/CONSOL-01-migration-plan.md`).

## Goal
An admin opens one page, `/admin/analytics`, titled "Feature Analytics", and sees (1) a Health strip of KPI tiles and hourly charts, then (2) feature outcomes, (3) AI usage and (4) AI quality, for a reporting period chosen at the top right. All figures come from recorded events only. A metric with no data source or incomplete data says "Unavailable" with a reason; nothing is mocked, sampled or estimated. No chat message text is ever shown. It merges US-ADM-01-01 to 03 and US-ADM-06-01 to 02 and removes the old boundary that kept AI call counts out of feature analytics. Stories: US-ADM-07-01 to US-ADM-07-08.

## Phases (what is built when)
- **Phase 2 (build on existing data):** all UI; backend endpoints `/health`, `/hourly`, `/daily`, `/chatbot-users` reading the existing ADM-01 tables (`analytics_chat_request`, `analytics_generation_attempt`, `analytics_practice_attempt`); the kept endpoints. Metrics whose source does not exist yet show `Unavailable: collection of this metric has not started` (logins, practice drafts started, practice sets published, rate-limited requests, failure categories).
- **Phase 4 (new collection, marked "(phase 4)" below):** hourly request log (outcome, failure category, latency; kept 30 days; includes in-progress and rate-limited requests), login events (kept 400 days), practice-draft-started events and practice-published events (both kept as long as attempts). The same endpoints then return real values; response shapes do not change.
- **Phase 5:** old pages, routes and specs deleted. Not part of this spec's build.

## Behaviour

### Page header
- Left: heading level 1 "Feature Analytics". Under it one muted line: "Recorded data only. Dates are UTC; chart times are shown in your local time ({timeZone})." (`{timeZone}` is the browser IANA zone, or "local time" if unknown).
- Right (one compact group, wraps under the title on mobile): the reporting-period selector, the text "Last updated {time}", and an icon button named "Refresh" (refresh icon, tooltip "Refresh"), all in one row to the right of the title on wide screens.

### Reporting period
- Compact select (combobox) named "Reporting period" with options "Today (UTC)", "Last 7 days" (default), "Last 30 days", "Custom range". Presets are UTC calendar dates ending today (UTC): Today = today..today; Last 7 days = today-6..today; Last 30 days = today-29..today.
- "Custom range" opens a small dialog "Custom range" with date fields "From date" and "To date", primary "Apply period" and "Cancel". When a custom range is active the select shows "{from} to {to}".
- Period rules (same as ADM-01): dates are exactly `YYYY-MM-DD` after trimming, both inclusive, UTC, From on or before To, at most 366 days. New client rule: the end date cannot be in the future (UTC). The server does not reject a future end date on the kept ADM-01 endpoints (unchanged); the AI usage endpoint does (ADM-06 rule).
- The period is kept in the URL: `?range=today|7d|30d` or `?from=YYYY-MM-DD&to=YYYY-MM-DD`, plus `workflow=student_exercise|teacher_lesson_planning` for the Quality section. No parameters means Last 7 days. Invalid values are replaced by the defaults.
- **Partial coverage (decided; deviates from ADM-01 AC12 and the ADM-01 recording rule):** if the period starts before a metric's recording start date, the metric is computed over the covered part only, from the recording start date (UTC) to the end of the period, and its response carries `data_starts_on` (the first covered date). The block shows the note "Data starts on {date}. Earlier days in this period are not included." Rates, medians and totals describe the covered part only. If the whole period ends before the recording start date, the metric is `unavailable` (`period_before_recording`). There is no backfill, except the phase 4 backfill of the request log in `plan.md`. This applies to the kept ADM-01 endpoints (`/usage`, `/generation`, `/quality`) when read by the hub and to every new endpoint; `/api/admin/ai-usage` (ADM-06) keeps its stricter rule (decided): any period that starts before the feature's coverage start, or touches a coverage gap, is unavailable for that feature; Open question 21 covers the one-off cleanup of older incomplete usage records. See "Deviations from ADM-01 and ADM-06".
- Hourly data (charts, and the rate-limited tile) is kept 30 days. If the period starts earlier than 30 days ago, the covered part starts at the retention floor and the same "Data starts on" note applies; if the whole period is older, the metric is `unavailable` (`beyond_retention`).
- The AI usage section covers at most 31 days ending today or earlier (ADM-06 rule). For a longer period it shows an explanation and sends no request.

### Section 1: Health
1. **KPI strip** (first content under the header), six tiles, each with a label, a value, one line of detail and, where it applies, a status chip:
   - **Chatbot success rate (display amended 2026-11-12; the API still returns the failure count and rate):** successful ÷ finished student chatbot requests received in the period (all modes). Requests still in progress (no outcome yet, received less than 2 minutes ago) are excluded from the numerator and denominator and shown as the note "{n} in progress"; a request with no outcome 2 minutes after receipt counts as unsuccessful with category `timeout` (see "In-progress requests"). Status chip applies.
   - **Generation success rate (display amended 2026-11-12):** successful ÷ generation requests (study notes and MCQ batches together). **Decided change to ADM-01-02:** from phase 4, requests refused by the rate or busy limiter count as generation requests and as unsuccessful (the old rule excluded them). Before phase 4 they are not recorded, so the rate covers accepted attempts only and the detail line says so. Status chip applies.
   - **Rate-limited requests:** count of requests (chatbot and generation) whose failure category is `rate_limited`, next to the total finished requests (phase 4; phase 2: `Unavailable: collection of this metric has not started`). No chip.
   - **Two response-time tiles (decided):** "Chatbot response time" and "Generation response time", each showing the median and the p95 together. Chatbot uses finished chatbot requests; generation uses finished generation requests (study notes and MCQ batches together); the two are never mixed. Each tile has a compact three-option selector, "All" (default), "Successful" and "Failed", which switches the tile between three sets of the same requests: all finished requests, successful requests only, and failed requests only. **Failed includes timed-out requests** (expired in-progress requests count as failed with 120 000 ms) and, for the chatbot, rate-limited and other failed requests that have a recorded duration. The selector is client-side (all three sets arrive in the one `/health` response, 0 extra requests), is remembered while the page stays open (including across Refresh and period changes) and resets to "All" on a browser reload. If the selected set is empty the tile says "No requests", never 0 or a time. Requests in progress are excluded; an expired in-progress request counts as a timeout with duration 120 000 ms; rate-limited generation requests have no duration and are left out. The detail line states how many of the requests failed or timed out, so the figure is not read as a success-only time. The Quality section's response time (successful responses only, ADM-01-03) is unchanged and labelled so. Median: middle value (mean of the two middle values for an even count), rounded to whole milliseconds half up. p95: nearest-rank (value at position ceil(0.95 × n) of the sorted durations). No chip.
   - **Practice completion:** as ADM-01-01: attempts started in the period that were submitted (whole set) by the end of the period ÷ attempts started, one decimal; `Not applicable` when none started. No chip.
2. **Status chip rules** (success-rate tiles only; the thresholds are unchanged and only read from the success side: failure rate above 5% is success below 95%; evaluated on exact counts, not on the rounded percentage): fewer than 20 requests (or attempts) → "Low sample", no colour; otherwise rate above 5% → "Critical" (red); 2% up to and including 5% → "Warning" (amber); below 2% → "Healthy" (green). Chip words: "Critical: below 95%", "Warning: 95% to 98%", "Healthy: 98% or above". Every chip shows an icon and the words, never colour alone. Values are shown with the chip, including for Low sample.
3. **Charts**, three cards side by side on wide screens (stacked on narrow): "Requests per hour" (stacked bars, successful and failed), "Failure rate per hour" (line with a dashed reference line at 5%), "Peak hours" (heatmap, weekday by hour). Each chart counts requests that have a recorded outcome: chatbot requests and generation requests together, including rate-limited generation requests. In-progress requests are not in the charts or rates; the chart cards show the same "{n} in progress" note as the tile, and an expired request is counted as a failed `timeout` in the hour it was received, so tile and charts always agree.
   - Hourly buckets are UTC hours on the server and in the API. The browser converts each bucket start to local time for labels, tooltips, tables, CSV and the heatmap's weekday and hour (weekday order Monday first; a bucket belongs to the local hour of its local start time).
   - Hovering a bar shows count and failure percentage; hovering a failure-rate point or a heatmap cell shows its values (exact copy in the UI table).
   - At most two cards per row (the third spans the full row). Hovering a card enlarges it slightly; clicking anywhere on the card opens the large view (AC43). Each card also has an "Expand" button opening a larger modal overlay with the chart, a data table, "Download CSV" and "Close"; focus is trapped; Esc closes; names are accessible. CSV is built in the browser from the loaded data, with no request.

### Section 2: Feature outcomes (lower urgency)
- **Daily activity** (UTC calendar days): "Logins per day" with unique active users split by role, student and teacher, plus a total of the two (phase 4; **admins are excluded** from logins-per-day and unique active users: admin sign-ins are not recorded as events); "Practice drafts started per day" by teachers (phase 4) and "Practice sets published per day" (phase 4), two distinct metrics with separate series and cards. **Drafts started:** a teacher's first save of a new practice set, recorded once per practice set by the draft-started event on that first save, whatever happens later (editing, publishing, deleting or never publishing); a duplicate or copy is a new practice set and counts as its own draft. **Published:** a practice set moving to the published state, recorded once per practice set by the published event at its first publication; unpublishing does not remove or change the count, and republishing adds nothing (the set stays counted on the day of its first publication). A set saved already published in one step counts once as a draft started and once as published, on the same day. Also "Attempts started and submitted per day" (funnel) and "Attempts per student per day" (median and distribution of attempts started per student per day). Each card is a small chart with a "Show data table" disclosure.
- **Chatbot requests by user:** table of successful and unsuccessful counts per user with failure rate, a role tab ("Students", "Teachers"), sortable columns, 10 rows per page, default order most unsuccessful requests first (top 10 by failures). Role totals and the grand total are shown above the table. Teacher chatbot data stays `Unavailable: this activity is not recorded` while no teacher chatbot exists (ADM-01 Open question 1).
- **Generation reliability:** the ADM-01-02 table (study notes, MCQ batches; requests, successful, unsuccessful, success rate), counting limiter-refused requests from phase 4.

### Section 3: AI usage (from ADM-06)
- Feature combobox "Feature" (All features by default) and the ADM-06 table "AI usage by feature": requests (service-call attempts including retries), failures, rate-limit failures, other failures, input, output and total tokens, each with its coverage text and exact unavailable reasons. Operational counts only; no outcome percentages, estimates or content. The period is the page period (31-day limit above). ADM-06's coverage rule is unchanged (unavailable if any part of the period predates coverage or touches a gap).

### Section 4: Quality (from ADM-01-03)
- The advisory notice, workflow tabs ("Student exercises", "Teacher lesson planning"), quality grades, response time, session activity, associated activity time, the assessed-responses table with pagination, and the admin-started grading run (button, confirmation, progress, privacy states). Behaviour, limits and privacy rules are exactly those of ADM-01 including its approved privacy amendment (local privacy gate, strict mode, blocked items); they are listed in "Retained criteria" and the UI table.

## Acceptance criteria
Criteria copied from the user stories are marked "(story)"; stories US-ADM-07-04 to 07 repeat the old stories' criteria verbatim.

### Access and platform
- [ ] AC1 Every new endpoint (`/health`, `/hourly`, `/daily`, `/chatbot-users`) rejects an unauthenticated request (401) and a student or teacher (403) with the shared behaviour; an admin succeeds; every response carries `Cache-Control: no-store`.
- [ ] AC2 The period validates as in ADM-01 (`invalid_date`, `period_order`, `period_too_long`); `/chatbot-users` also validates `role` (`invalid_role`), `sort`/`order` (`invalid_sort`) and paging (`invalid_paging`) with the exact codes and messages in `plan.md`; order of checks is fixed there.
- [ ] AC3 (phase 4) Every recording hook added or extended by this feature never raises and never changes the host route's status code or body, even when the analytics tables are unavailable; failures are logged without request content.
- [ ] AC4 No new endpoint response contains chat text, prompts, replies, generated content, email addresses, IP addresses or credentials. Only `/chatbot-users` returns user ids and display names (as `/usage` did).

### US-ADM-07-01 Health strip
- [ ] AC5 `/health` returns the six tile metrics (chatbot failure, generation failure, rate-limited, chatbot response time, generation response time, practice completion) for the period with the shapes in `plan.md`; each is independently `available`, `not_applicable` or `unavailable`; a failed read of one is `unavailable`/`read_failed` and the others are still returned (carries ADM-01 AC12's second sentence; its first sentence is replaced by AC39).
- [ ] AC6 Failure-rate severity is `low_sample` below 20 requests (attempts), else `critical` when `failed*100 > 5*total`, `warning` when `2*total <= failed*100 <= 5*total`, else `ok`. Boundary cases in the test plan (for example 20 requests with 1 failure is 5.0% and `warning`; 50 with 1 is 2.0% and `warning`; 51 with 1 is `ok`; 19 requests all failed is `low_sample`).
- [ ] AC7 The tile shows icon plus text for each severity; colour is never the only signal (UI table); contrast meets WCAG AA in light and dark themes.
- [ ] AC8 `/health` returns separate `chatbot_response_time` and `generation_response_time` objects. Each has three sets, `all`, `successful` and `failed`, each with `count`, `median_ms` and `p95_ms`, over finished requests of its own workflow with a recorded duration (never mixed across workflows). `failed` includes timed-out requests; an expired in-progress request is failed with 120 000 ms; in-progress requests and rate-limited generation requests (no duration) are excluded from every set; `all.count = successful.count + failed.count`; p95 is nearest-rank; an empty set has `count` 0 and `null` median and p95 (the UI says "No requests", never 0).
- [ ] AC9 Practice completion in `/health` equals the ADM-01-01 definition (carries ADM-01 AC8-AC10).
- [ ] AC10 (phase 4) Rate-limited requests counts request-log rows with category `rate_limited` in the period; before phase 4 it is `unavailable`/`not_collected`; if the period starts before the request log's category start, only the part from that date is counted and `data_starts_on` is set (unavailable/`period_before_recording` only if the whole period is earlier).

### Request log, retention and backfill (phase 4)
- [ ] AC33 Every chatbot request is logged at receipt (outcome `pending`) and updated once with its outcome, failure category and latency; every generation request that was accepted or refused by the rate or busy limiter produces exactly one request-log row. Rate-limited generation requests are logged (category `rate_limited`) and counted as generation requests in the reports (AC40) but still create no `analytics_generation_attempt` row and no grading item.
- [ ] AC34 Category mapping: `LlmRateLimited`/`LlmBusy` → `rate_limited`; `LlmTimeout` → `timeout`; `LlmReplyCutOff`, `LlmBadResponse`, an empty or invalid reply or output failing validation → `invalid_output`; `LlmUpstreamError`, `LlmNotConfigured` and other `LlmError` → `upstream`; anything else → `unclassified`. Successful rows have no category.
- [ ] AC35 Request-log rows older than 30 days are deleted by the purge; reads ignore rows older than the retention floor even if not yet purged; the log holds no user id and no text.
- [ ] AC36 The phase 4 migration backfills the last 30 days from existing chat and generation rows (category `unclassified` for failures), is idempotent, and records the date from which categories are real.
- [ ] AC37 Concurrency: two simultaneous outcome calls for one request leave one log row with the first outcome; two simultaneous login hooks create two events (one per login); two draft-started hooks (or two published hooks) for one practice set create one row each; publish, unpublish and publish again leaves one published row with the first time.

### In-progress requests, partial coverage, changed definitions
- [ ] AC38 A chatbot request with no outcome whose age (server clock at read time minus receipt time) is under 120 seconds is "in progress": excluded from every rate, count, percentile and chart bucket, and reported as `in_progress` (count) by `/health`, `/hourly` and `/chatbot-users`. At 120 seconds or more with no outcome it is counted as unsuccessful with category `timeout` in the hour it was received, with duration 120 000 ms. The rule is applied at read time (no write); an outcome that arrives later replaces it with the real outcome. The tile, charts and per-user table use the same function, so their totals agree for the same instant. In-progress generation requests are not visible (a generation attempt is recorded after the AI call returns), so their `in_progress` is 0.
- [ ] AC39 Partial coverage: when the period starts before a metric's source start date (or before the 30-day retention floor for hourly data), the response covers the part from that date, sets `data_starts_on` to it, and the block shows "Data starts on {date}. Earlier days in this period are not included."; `data_starts_on` is `null` otherwise; the metric is `unavailable` only if the whole period precedes the source (or retention).
- [ ] AC40 (phase 4) A generation request refused by the rate or busy limiter counts as a generation request and as unsuccessful in the generation failure tile and the "Generation reliability" table (`requests = attempts + rate_limited`; rate = successful ÷ requests). Before phase 4 the numbers cover attempts only and the table says "Rate-limited requests are not recorded yet."
- [ ] AC41 `/daily` returns `practice_drafts_started` (per UTC day, from first-save events) and `practice_published` (per UTC day, from first-publication events) as separate series; the page shows two cards, "Practice drafts started per day" and "Practice sets published per day".
- [ ] AC42 (phase 4, migration) The AI usage cleanup in `plan.md` never runs automatically and permanently deletes the older incomplete usage records with no archive kept. `--dry-run` changes nothing and prints the row counts that would be deleted; `--apply` refuses to run without the explicit approval flag, deletes only `pending` attempts older than the cut-off, never moves a coverage start earlier, and is irreversible.

- [ ] AC46 AI usage collection switch: an admin can turn collection on or off for STU-03 and TEA-02 with `PUT /api/admin/ai-usage/coverage` body `{"enabled": boolean}` (admin only: 401/403; strict body, else 422; CSRF required; 10 per 60 s per admin, 429; failure 503 "AI usage data is temporarily unavailable. - [ ] AC47 Development only: `src/backend/dev_seed.py` (refuses unless `APP_ENV=development`) runs the dev seeds in order, including `feature_analytics.seed_dev` (about a week of made-up hub activity written through the real recording hooks, once per database, `--force` for another week) and activates AI usage collection. Never used in production; its rows look like recorded data, so it must not be run where real usage is recorded.

### Deviations from ADM-01 and ADM-06 (user-decided, 2026-11-11)
| Old rule | New rule in ADM-07 | Why |

In-flight requests are aborted on unmount, period change and Refresh; stale responses are ignored.
- Wrong role: A signed-in student or teacher opening `/admin/analytics` is redirected (history replace) to their own home area (`homePath(role)`), and no analytics request is sent. - Link history: push or replace: nav link "Feature Analytics": push. Choosing a different period preset: push. Applying a changed custom range: push. Workflow tab switch: replace. ## Security and AI safeguards
- Access: only active admins use `/api/admin/analytics/*` and `/api/admin/ai-usage`; checks are server-side with the shared admin dependency; the page also redirects other roles but the server is the control. No endpoint accepts a user id, course id or record id from the client other than the grading run id. Responses are `Cache-Control: no-store`.
- Private data: new tables hold counts, enums, timestamps and ids. The request log holds no user id and no text. Login events hold user id, role and time only. `/chatbot-users` returns display names and ids for admins only. Nothing in the hub is logged with request content. All names and values render as plain text; CSV cells are numbers, ISO times, fixed labels or weekday names, so no user text reaches a CSV (no formula injection).
- AI: the hub adds no new AI call. Grading (section 4) keeps every ADM-01 safeguard (SoC LLM only via the shared client, local privacy gate, 20 items per run, one run at a time, 10 runs per rolling hour, no retries, no answer keys). AI usage reads metadata only.
- Limits (SHR-03): period at most 366 days (31 for AI usage); `/chatbot-users` limit at most 100; `/hourly` returns at most 31 × 24 buckets; AI usage report throttle of 30 per 60 seconds per admin (ADM-06) applies to Refresh and period changes.
- Concurrent requests (same time): hooks stay idempotent per record (outcome applied once; one request-log row per request; one draft-started row and one published row per set); the purge and a recording write cannot corrupt each other (row-level deletes by age); two Refresh clicks cannot start duplicate loads (button disabled while pending); grading start rules unchanged (one 202, the rest 409).
- Normalisation: dates trimmed and exactly `YYYY-MM-DD`; `workflow`, `role`, `sort`, `order`, `feature` trimmed and compared exactly in lower case (feature ids as in ADM-06); `limit` and `offset` base-10 integers; hour buckets are the UTC hour of the stored UTC timestamp; local conversion happens only in the browser.
